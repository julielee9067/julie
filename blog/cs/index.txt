# μ-Kernel

## 개요
* 초창기 마이크로커널이 느리고 경직되어 보였던 이유는 개념 자체의 한계가 아니라, **커널이 과도하게 비대**했고 **하드웨어 특성을 살리지 못한 구현** 때문
* 해결책: **커널에 ‘불가피한 메커니즘’만 남기는 것**. 즉, 보호와 자원 다중화를 위한 **최소 추상**만 커널에 두고, 정책·고급 기능은 모두 사용자 공간으로 내림

## μ-커널의 최소 API
1. **주소공간(Address Space)** + **세 연산**
   * **grant(양도)**: 페이지 소유권을 다른 주소 공간으로 넘김(보낸 쪽 매핑 제거). 중간 페이저가 끼어도 소유권 경로가 단순해지고 내부 매핑이 불어나지 않음.
   
   * **map(공유)**: 보낸 쪽에도 매핑을 유지한 채 **공유 매핑**을 만듦. 공유 메모리, CoW 같은 패턴을 사용자 공간에서 구현.
   
   * **flush(제거)**: 자신의 주소 공간 안에서 특정 매핑을 제거하고, 그 매핑에서 파생된 하위 매핑도 연쇄적으로 무효화. 타인의 매핑은 제거할 수 없으니 보호 보장.
   
   * **I/O 권한 일원화**: 메모리-맵드 I/O·포트 접근도 페이지 단위 권리로 관리(메모리와 동일한 규율로 **grant/map/flush**).
> 구현 관점: 물리 프레임마다 “매핑 트리”를 두어 어떤 주소 공간·가상 페이지가 그 프레임을 참조하는지 지역적으로 기록하면 grant/map/flush가 빠르고 안전해짐.

2. **스레드(Thread)**
   * 특정 주소 공간에 결박된 실행 컨텍스트. 
   * 스레드 전환은 종종 주소 공간 전환을 수반하므로, 커널이 주소 공간 무결성과 관련된 상태 변화를 엄격히 통제.

3. **IPC(프로세스 간 통신)**
   * **메시지 기반 통신**을 기본 원시로 두고, 이것으로 RPC 같은 상위 추상 구성.
   * **인터럽트를 IPC로 모델링**하면, 드라이버도 사용자 공간에서 만들 수 있음 (커널은 장치 의미에 관여하지 않고, 인터럽트는 특정 ID의 “빈 메시지”로 전달).

4. **UID(고유 식별자)**
   * 스레드·태스크·채널을 **공간·시간 전역**에서 확실하게 구분하는 값. 로컬 통신에 과한 암호학 대신, **커널이 싸게 제공하는 UID**가 실용적임.

## 왜 이 네 가지면 충분한가? (유연성의 실증)
* **유저 수준 페이저/메모리 관리자**: 일반 VM부터 데이터베이스 특화 매핑까지 정책을 자유롭게 설계·합성할 수 있음 (겹겹이 쌓는 “스택형” 구성도 자연스럽게 가능).
* **드라이버** : 장치 레지스터를 매핑하면 **순수 사용자 프로세스**로 구현됨 (부트 단계만 예외적으로 도와주고 이후 제거).
* **네트워크/원격 통신**: IPC 서버가 네트워크 프로토콜을 로컬 IPC처럼 제공하고, 공유 버퍼는 map으로 전달
* **UNIX 성격**: **페이저 + IPC 서버 조합**으로 전통적 OS 성격도 위에서 구현할 수 있음.

## 성능
* **커널 ↔ 유저 전환**은 하드웨어가 제공하는 최저치에 근접하도록 만들 수 있음. 과거의 큰 비용은 커널 내부 경로가 비대해서 생긴 현상
* **주소 공간 전환**의 진짜 비용은 “전환”이라는 개념 자체보다 **TLB 구조와 재적재 방식**에 달려 있음. 적절한 설계로 매우 낮은 수준까지 줄일 수 있음.
* **IPC**도 경로 다이어트와 작업셋 관리만 잘하면 짧은 지연으로 구현됨. **인터럽트를 메시지로 처리**하는 구조가 실용적일 만큼 충분히 빠르게 만들 수 있음.
* **캐시/TLB 간섭**은 정렬·배치·재적재 최소화 같은 구현 기술로 상당 부분 억제할 수 있음

## 프로세서 의존성(“커널 자체 이식성”의 재해석)
* 효율 좋은 μ-커널은 트랩·TLB·세그먼트·캐시 같은 CPU 디테일에 맞춘 설계가 필수 (아키텍처별로 달라져야 함)
* **그 위에 얹힌 시스템(서버·라이브러리)** 의 이식성은 그대로 유지

## 관련 작업과 포지셔닝
* **Synthesis**: 커널 경로 특수화를 위해 동적 코드 생성을 썼지만, 현대 CPU에서는 코드 팽창·I-캐시 압력 문제가 큼.
* **SPIN**: 언어 기반 보호로 커널 내부 확장을 허용해 경계 횡단을 줄이지만, 커널 모드 실행과 주소 공간 효과는 남음. 컴파일러 기술과 μ-커널의 결합이 유망.
* **Mach 변종들**: IPC 의미론을 조정했지만 최소 μ-커널 경로 대비 여전히 무거움.
* **Exokernel**: 저수준 다중화를 직접 노출해 매우 빠른 보호된 제어 이전을 보여줌(대신 인터페이스가 아키텍처에 더 민감).

## 결론
* **최소 메커니즘**(주소공간 grant/map/flush, 스레드, IPC, UID)만으로 **임의의 OS 성격**을 위에 구축 가능
* 성패는 **적절한 추상 선택**과 **대상 CPU에 맞춘 경로 설계**, **실측 기반 튜닝**에 달려 있다. 공개된 **L4**가 실험 기반을 제공

# Improved Address-Space Switching on Pentium

## 문제: Untagged TLB의 전환 비용
486/Pentium 등 **ASID 없는(TLB에 주소공간 태그가 없는)** CPU에서는 주소 공간 전환 시 **CR3 교체 → TLB 플러시**가 일어나고, 이후 **TLB 리필**이 전체 비용을 지배함. 

TLB가 클수록 더 아픔.

## 해법(세그먼트 기반 “small-space” 멀티플렉싱)
* **여러 개의 `작은 사용자 공간(small spaces)`** 을 하나의 사용자 선형 공간 내부에 공존시키고,
* 전환 시 **CR3는 건드리지 않은** 채, 사용자 평면 세그먼트의 **base/limit(디스크립터)만 수정**해 다른 작은 공간을 가리키게 만듦
* 사용자 입장에서는 **같은 세그먼트 선택자를 계속 쓰므로 완전 투명**하고, μ-커널 API도 바꿀 필요가 없음.

## 메모리 배치와 전환 분기(개념)
* 사용자 주소 공간을 **일반적인 `큰 공간` 영역**과 **모든 태스크가 공유하는 `작은 공간 창`** , 그리고 **커널 영역**으로 나눔 (정확한 비율은 중요치 않음).
* **전환 분기**
  * **Large→Large(서로 다른 태스크)**: 기존 방식대로 **CR3 교체(플러시 불가피)**
  * **Large→Small / Small→Small / Small→직전 Large**: CR3는 유지, 디스크립터만 갱신 후 데이터 세그먼트 레지스터를 리로드하여 새 base/limit을 반영

## IPC 경로와 복사 경로 최적화
* 커널은 진입 시 커널 전용 세그먼트로 전환해 안전을 확보한 뒤, 대상이 작은 공간 경로면 **디스크립터 갱신 + 세그먼트 리로드**만 하고 사용자로 복귀
* **복사 최적화**: 작은 공간 창 덕분에 송·수신 버퍼가 커널에서 동시에 보이는 구성이 가능 -> **임시 매핑 없이 바로 복사** 가능.

## 동적 분류와 압력 대응(자동·투명)
* 상단 사용자 영역을 쓰지 않는 태스크는 자동으로 작은 공간으로 분류됨. 이후 상단을 매핑하면 **큰 공간으로 승격**됩
* 작은 공간 슬롯이 부족하면 휴면 중인 **작은 공간들을 큰 공간으로 되돌려 슬롯 회수**
* 이 모든 과정은 **사용자에게 투명하며, API 변경이 필요 없음**

## 언제 이득이 큰가?
* **작은 작업셋**을 가진 **짧은 서버/드라이버**들이 **IPC를 자주 하는** 워크로드에서 효과가 극대화됨
* **Large ↔ Large 전환**은 본질적으로 작업셋 재구축 비용이 커서, 이 방법으로도 완전히 상쇄되지는 않음 (그 구간은 기존 비용을 그대로 감수).

## 다른 CPU와의 대비(왜 접근이 다른가?)
* **ASID가 있는 CPU(MIPS 등)** 는 원래 전환 시 TLB 플러시가 필요 없으므로 이런 트릭이 크게 의미 없음
* **PowerPC**는 세그먼트 레지스터로 상위 주소 공간 교체를 직접 지원해 전환이 본질적으로 가벼움
* **486/Pentium**처럼 ASID가 없는 경우엔, **세그먼트 디스크립터 갱신**으로 **ASID**와 유사한 효과를 소프트웨어적으로 흉내 내는 것이 포인트

# Review Questions

### Sketch how you will implement a device driver using the primitives provided by Liedtke's microkernel.
#### Assumptions
* **A0 주소공간**: 물리 메모리와 장치 MMIO(메모리-맵 입출력) 영역을 있는 그대로 볼 수 있는 “물리 뷰” 주소공간.
* **커널이 주는 primitive** : 주소공간(태스크), 스레드, **동기 IPC**, 주소공간 연산 **map/grant/flush**
  * **map**: 내 것도 남겨둔 채 **공유** 매핑 만들기
  * **grant**: **소유권 통째로 양도**(보낸 쪽 매핑은 사라짐)
  * **flush**: **내 주소공간에서** 매핑 지우기(거기서 파생된 것까지 연쇄 무효화)
  
* **인터럽트=IPC**: 특정 IRQ가 오면 커널이 해당 “인터럽트 스레드”로 **짧은 메시지를 보냄** → 스레드가 깨어나 처리.

#### Steps
1. **드라이버 태스크/스레드 만들기**
   * 태스크 `kbdd`를 만들고,
   * **Top-half 스레드**(IRQ를 직접 받음) + **Bottom-half 스레드**(해석·발행)를 분리
     → 짧고 반드시 바로 해야 하는 일(레지스터 읽기)은 Top-half, 비교적 긴 일(스캔코드 해석, 구독자 통지)은 Bottom-half로 넘겨 **지연 격리**.

2. **장치 레지스터 매핑하기**
   * A0에서 키보드 **status/data 레지스터**가 들어있는 MMIO 페이지를 `kbdd`에 **grant**(독점이 필요할 때) 또는 **map**(공유가 필요할 때).
   * 규율: **한 주체가 책임지고 만지는 게 안전** (Integrity를 위해 독점 선호)

3. **IRQ를 드라이버에 묶기**
   * 커널에 `IRQ_KBD → kbdd.top`로 라우팅 설정. 인터럽트가 뜨면 **짧은 IPC**가 Top-half 스레드로 도착해서 즉시 깨어남

4. **Top-half(인터럽트 핸들러) 작업**
   * **status** 점검 → **data** 레지스터에서 스캔코드 읽기 → **lock-free 링버퍼**에 넣기 → 필요 시 장치 쪽 정리(EOI 등).
   * 링버퍼가 있는 페이지 `kbd_buf`는 **클라이언트(콘솔/윈도우 시스템 등)에 읽기 전용 map**으로 공유하거나, 소량 데이터면 IPC 페이로드로 바로 보냄. (교차 주소공간 복사가 필요하면, 커널의 임시 매핑 경로를 써서 **추가 맵 없이 복사** 가능.)

5. **Bottom-half(발행/서비스 API)**
   * 스캔코드 → 키 업/다운·조합키 상태로 해석, 자동반복 처리.
   * 클라이언트 요청은 **동기 IPC**로 응답: `READ(n)`, `SUBSCRIBE(필터)`, `GET_STATE()` 등.
   * 성능 팁: IPC는 스레드 전환=주소공간 전환이므로 **메시지 크기를 작게**(레지스터·작은 버퍼) 유지.

6. **보호와 회수(Integrity/Revocation)**
   * 클라이언트가 죽거나 공유를 끝내고 싶으면, 드라이버가 해당 페이지를 **flush**해서 상대쪽 매핑을 **무효화**.
   * 소유권 규율은 **grant/map/flush** 조합으로 깨끗하게 유지.

> **디스크로 확장**: 동일한 틀에 “요청 큐 + DMA 준비(PRD/SG 테이블) + 완료 인터럽트 처리 + 오류/타임아웃 재시도 + 필요 시 바운스 버퍼(grant로 확보)”만 얹으면 됨

### What is the difference between a "thread" as defined in Liedtke's paper and a Strand in SPIN?
* **L3/L4의 스레드**: 커널이 스케줄하는 **고정 단위**(특정 주소공간에 묶여 있음). IPC는 기본적으로 **동기**라서, 스레드 전환은 자주 **주소공간 전환**을 동반. 커널의 TCB가 전환에 필요한 커널 상태(페이지 테이블 루트 등)를 잡고 있음.
* **SPIN의 Strand**: 확장(라이브러리 OS)에게 내주는 **정책-주도형 스케줄 추상**. 쉽게 말해 “가상 CPU 조각”으로, 확장이 **자기 런큐/우선순위/규칙**을 얹어 **앱 맞춤 스케줄링**을 구현. 다만 **전역 스케줄러**는 CPU 배분의 최종 권한을 갖고 안전 보장

**핵심 차이**
* L3/L4 스레드 = **커널의 정해진 단위**.
* SPIN Strand = **확장이 정책을 얹을 수 있는 단위**(인-커널 안전 호출로 성능 유지).

### 전환 오버헤드 줄이기 (아키텍처에 맞춘 두 전략)

### Explain the notions of "independence" and "integrity" in the L3 microkernel.
* **Independence**: 각 서브시스템은 **자기 주소공간/스레드**만 다루고, 상호작용은 **명시적 IPC**와 **명시적 map/grant**로만 함. **암묵 공유가 없으니** 구조적/장애 격리가 자연스럽게 됨.
* **Integrity**: **소유자만** 해당 자원(페이지 등)을 **map/grant/flush**할 수 있음. 또한 소유자는 자신에게서 **파생된 매핑**을 **flush**로 연쇄 무효화할 수 있어, **무단 수정 경로가 구조적으로 차단**.

### “grant(소유권 양도)”가 무결성을 해치나?
원문: All the subsystems in L3 live in user space. Every such subsystem has its own address space. The address space mechanism "grant" allows an address space to give a physical memory page frame to a peer subsystem. Can this compromise the "integrity" of a subsystem? Explain why or why not.

**해치지 않음**
* **grant는 자발적 소유권 이전**이라, 보낸 쪽 **매핑이 사라짐**. 즉, 그 페이지를 통해 보낸 쪽 상태가 더 이상 영향을 받지 않음(보낸 쪽 무결성 OK).
* 받는 쪽은 그 데이터를 **자신의 정책**에 따라 검증·사용하면 됨(데이터 출처 신뢰는 각자 정책 문제).
* 나중에 노출을 거둬들이고 싶다면, 소유권 흐름 위쪽에서 **flush**로 파생 매핑을 무효화하면 됨.

### "Trust in the L3 microkernel is transitive." Explain what this sentence means.

* 모두가 **커널의 참조 모니터**(규칙 집행자)를 신뢰한다는 것이 1차 전제
* 여기에 A가 B에게 **map/grant/IPC**로 **무언가를 공유**하면, 그 **공유 범위 안에서는** A의 올바름이 **B의 행위**에도 달리게 됨. 즉, **A → (커널, B)** 로 **신뢰 전이**.
* 중요한 점은 이 전이가 **명시적**이라서 **범위가 작고 추적 가능**하다는 것임. 그래서 μ-커널은 `최소 메커니즘 + 명시적 공유`를 고집.

### Microkernel based OS will always be less efficient compared to Monolithic kernel. True or False?  Explain your answer in detail.

**거짓**

* μ-커널도 **경계 횡단과 주소공간 전환을 얇게** 만들면 충분히 빠름(인터럽트를 IPC로 처리할 만큼).
* 모놀리식은 **커널 내부 공위치(co-location)** 덕을 볼 수 있지만, μ-커널도 **CPU 특성에 맞춘 경로 설계**로 충분히 대등하거나 더 빠를 수 있음.

## 개요

> **Exokernel**: 커널은 보안만 담당(`"누가 어떤 자원을 써도 되는가?”`), **정책/기능은 앱 옆의 라이브러리 OS(LibOS)** 로 내려보내 각 앱이 자기 상황에 맞게 OS를 바꿔 쓰는 구조
* **빠른 이유**

  * 권한 확인을 **처음 한 번(바인딩 때)** 비싸게 하고, 그다음부터는 **짧은 표식(태그/엔트리)만 확인**해서 끝내기 때문(**secure bindings**)
  * 자원을 회수할 땐 먼저 알리고(**visible revocation**), 말을 안 들으면 **끊고 기록 후 복구를 촉구(abort)** 해서 **시스템 통제권**을 유지
* **커널 / LibOS**

  * 커널: **Aegis**
  * LibOS: **ExOS**

### 용어

| 용어             | 설명                                                              |
| -------------- | --------------------------------------------------------------- |
| **LibOS**      | 앱 전용 미니 OS. 파일/네트워크/스케줄링 등을 앱 내부 라이브러리로 구현해 링크해서 씀 |
| **Capability** | "이 자원을 이런 권한으로 써도 됨"을 증명하는 토큰                                   |
| **TLB/STLB**   | 주소 변환 캐시 (작은 하드웨어 캐시(TLB)) 앞단에 **큰 소프트웨어 캐시(STLB)** 를 두어 미스 비용 절감.                            |
| **PCT**        | Protected/cheap 교차 호출. 상대에게 남은 시간 조각을 기부하며 레지스터를 그대로 전달해 복사/문맥교환 비용 최소화.                                      |
| **DPF**        | 다운로드/컴파일 된 패킷 필터 (패킷 분류가 매우 빠름)                                 |
| **Scratch register**        | 함수 호출 간 보존되지 않아도 되는 임시 레지스터                                 |
| **Upcall**        | 커널 → 사용자 공간으로의 역방향 호출. 커널이 이벤트/예외/인터럽트 처리를 위해 **애플리케이션이 등록해 둔 함수(핸들러)** 를 직접 호출해 제어를 넘김                                 |

## 배경

* **커널 최소화**: 커널은 **primitive 자원(CPU, 물리 메모리, TLB, 예외/인터럽트, NIC)** 을 안전하게 여러 앱에 나눠주기만 함.
* **externalized policies**
  * VM/IPC/파일시스템/스케줄러 같은 **정책과 고급 기능은 LibOS**가 구현.
  * 앱이 필요한 것만 골라 쓰고, 내부 로직도 마음대로 바꿀 수 있음.
* **3요소**

  1. **Secure bindings**
    * 처음 연결할 때 신원확인·규칙설치(예: TLB 엔트리, 패킷 필터) → 이후 사용은 스티커 확인하듯 값만 체크.
    * 효과: 핫패스에서 검사 비용이 거의 0에 수렴.
    
  2. **Visible revocation**
    * 커널이 `“메모리 좀 돌려줘”`라고 정식으로 요청 → LibOS가 무엇을 반납할지 고르고 **자기 표(페이지 테이블 등)** 를 스스로 정리.
    * 효과: 커널-앱 상태 불일치가 줄어듦.
    
  3. **Abort**
    * 협조 안 하면 커널이 바인딩을 강제로 절단하고 `“무엇을 뺏었는지”` 기록을 남긴 뒤 예외를 올려 LibOS가 사후 복구하게 함.
    * 효과: 앱을 죽이지 않고 시스템을 안정하게 유지.
    
* **실험체**: **Aegis (커널) + ExOS (LibOS)** 로 실제 DECstation에서 **수치 비교**

## 설계 원칙

### 1) 보호 vs 관리의 분리
**커널=경비·출입 통제, LibOS=실사용 규칙/구현**

결과: 커널 인터페이스가 작고 안정적 → 빠르고 유연.

장점 예: 데이터베이스는 로그·버퍼 정책을, 게임은 스케줄링/메모리 핫패스를 각자 유리하게 교체 가능.

### 2) Secure bindings

**바인딩 시**: 권한증명(capability) 확인 + 짧은 코드/표식 설치(TLB 엔트리, DPF 등)

**사용 시**: 설치된 표식만 조회 → 시스템콜/트랩 없이 바로 통과 가능

**무효화 시**: 회수나 보안사유로 표식을 제거하면 이후 접근은 거부

### 3) Visible revocation

보이게 만들면 **LibOS가 자기 표를 즉시 갱신**하므로 `“커널은 회수했는데 앱은 모르는”` 불일치가 줄어 오류가 적음.

단, ASID처럼 상태가 없는 자원은 너무 자주 바뀌니 조용히(invisible) 바꾸는 편이 효율적.

### 4) Abort

LibOS가 응답이 느리거나 고의로 버틴다면:

  1. 커널이 바인딩을 끊고(자원 회수),

  2. Repossession vector(무엇을 뺏었는지 목록)에 기록,

  3. 예외를 올려 LibOS에게 `“이런 게 사라졌으니 표/상태를 고쳐라”`라고 통지.

이 절차로 시스템 전체는 멈추지 않음.

### 5) 공유 서버 최소화
공용 파일서버처럼 정책이 박히는 요소는 확장성의 적

가능하면 앱별 라이브러리로 분리해 정책을 다양화

### 6) 커널이 내주는 원시 기능 (Primitives)
Processor, Physical memory, TLB, Exceptions, Interrupts, DPF 기반 NIC

### 7) PCT (Protected Control Transfer)
* sync: 현재+다음 시간 조각까지 기부, 필요하면 반환.
* async: 남은 시간만 즉시 기부.
* 공통 보장: 원자적 도착, 앱이 보는 레지스터 불변 → 레지스터 자체가 메시지가 되어 복사/컨텍스트 스위치 비용 절감.
* 비유: 문서 보내기(IPC) 대신 **전화 통화(PCT)** 로 바로 말하는 느낌.

## Aegis 구현

* **예외 디스패치(업콜) 빠름**
  * 몇 개 스크래치 레지스터만 물리영역에 저장 → 유저 모드 핸들러로 점프.
  * 커널이 큰 프레임을 저장/복원하지 않아서 μs 단위로 빠름.
  
* **TLB 관리 + STLB**
  * TLB 미스 시 세그먼트/보장 여부를 먼저 본 뒤,
    * 보장 영역이면 커널이 즉시 TLB 설치(업콜 생략),
    * 아니면 LibOS 핸들러 호출
  * **STLB(4096 엔트리)** 가 용량 미스를 흡수 → 업콜 자체를 피하는 경우가 많아짐.* **PCT**
  
* **PCT**
  * Sync/Async 모두 지원, 레지스터 보존 + 시간 기부로 짧고 예측 가능한 경로.
  
* **DPF networking**
  * VCODE로 필터를 컴파일해 NIC 경로에 설치

## ExOS

* **제공 기능**
  * **Process, User-level exception, VM, IPC, Networking(ARP/RARP, IP, UDP, NFS)**
  
* **ExOS의 VM**
  * 약 1000줄로 구현했지만, 페이지 공유/별칭, 페이지별 캐시 정책, 특정 페이지 강제 할당, DMA까지 지원
  * 프로토타입 한계: 스와핑 없음, 선형 페이지 테이블(단순하지만 큰 작업셋에선 비효율 가능)
  * 커널이 정책을 강요하지 않으니, LibOS가 가벼운 핵심만 골라 성능 최적화에 집중할 수 있음

> 정책을 사용자 공간으로 끌어올려 커널 경로를 짧게 하고, 복사/컨텍스트 스위치를 줄여서 전체가 빨라진다.

### 1. A library OS implements paged VM on Exokernel; an app hits a page fault. Walk the steps until resumption. (State assumptions and full path)

* **가정**

  * Aegis는 물리 페이지와 TLB 설치 작업에 대한 capability를 노출하고, 대용량 STLB로 매핑을 캐시함

```
TLB miss / page fault
   ├─ STLB hit? ──► 커널이 즉시 TLB 재설치 ──► 재개
   ├─ 보장 영역? ─► 커널이 즉시 TLB 설치 ───► 재개
   └─ 그 외 ─────► LibOS 핸들러 실행
                     ├─ 유효+상주 → TLB 설치 요청 → 재개
                     ├─ 유효+불재 → 프레임 할당/교체(필요시 회수 대응) → 재시도
                     └─ 무효     → 세그폴트 전달
```

  1. 폴트/미스 발생 및 신속한 예외 디스패치
     애플리케이션이 매핑되지 않은 가상주소에 접근하여 TLB 미스/페이지 폴트가 발생 -> Aegis는 소수의 스크래치 레지스터만 고정된 물리 영역에 저장하고, 폴트 원인/주소를 적재한 뒤 사용자 모드의 등록된 핸들러로 제어 이양
     
  2. 보장 영역 판정 및 커널 직접 설치
     문제의 가상주소가 보장 영역에 속하는지 검사. 해당하는 경우, Aegis가 업콜 없이 TLB 엔트리를 직접 설치하고 실행을 즉시 재개

  3. LibOS 핸들러의 페이지 테이블 검토
     LibOS 핸들러는 자체 페이지 테이블을 조회

       * 무효/권한 없음: 애플리케이션에 세그멘테이션 폴트 보고
       * 유효·상주(resident): 대상 물리 페이지에 대한 TLB 엔트리를 구성하고, 접근 권한을 증명하는 capability와 함께 TLB 설치를 Aegis에 요청

  4. 커널 검증 및 TLB 설치 후 복귀
     Aegis는 제출된 capability가 요청된 접근 권한과 일치하는지 검증 -> 검증 성공 시 TLB 엔트리를 로드하고, 사용자 모드로 복귀. 이후 폴트를 유발한 명령을 재시도
     
  5. 비상주 페이지 처리(가져오기 및 교체)
     * 페이지가 상주하지 않는 경우, 핸들러는 프레임 할당 또는 정책(예: LRU)에 따른 교체를 수행
     * 자원 압박 시, 커널은 visible revocation으로 페이지 회수 요청을 발행할 수 있음. LibOS는 반납할 페이지를 선택하고, 더티 페이지라면 백스토어 기록 후 자체 페이지 테이블을 갱신
     * LibOS의 지연·비협조 시, 커널은 abort-repossess 절차를 통해 바인딩을 강제 해제하고, 회수 내역을 repossession vector에 기록한 뒤 예외를 발생시켜 메타데이터 복구 요구 → 애플리케이션을 종료하지 않고도 시스템 일관성을 유지.

  6. 재시도 / 재개
     페이지가 상주 상태가 되면, 3–4단계를 반복하여 TLB 설치를 완료함 -> 핸들러는 반환되고, 폴트를 야기한 명령이 정상적으로 재실행됨.

### 2. “The high-level goals of SPIN and Exokernel are the same.” Why is that true?

* 둘 다 확장성(앱별 정책), 안정성(강한 격리/보호), 성능(hot path의 함수 호출 수준 overhead)을 지향
* 접근법은 다름. Exokernel: low-level primitives를 노출 + 보안 다중화 위에 LibOS 정책을 얹음. SPIN: 안전한 커널 내 확장(language enforced interface, dynamic kernel link, event/handler)으로 달성

### 3. Map Exokernel mechanisms to corresponding SPIN mechanisms

#### 1) Secure bindings → (SPIN) Typed capabilities + 1회 해석 후 직접 호출
* 권한 검증을 **바인딩 시점**에 끝내 두고, **사용 시점**에는 짧은 표식 확인만으로 접근을 허용하는 방식.
* **Exokernel**: TLB 엔트리·패킷 필터 등 **바인딩 때 인가**를 붙여 두어 이후 접근은 **값(태그) 확인만**으로 처리.
* **SPIN**: **타입이 붙은 포인터(capability)** 와 **동적 링크**로 인터페이스 이름을 **한 번만 해석**하고, 그 이후에는 **도메인 간 호출이 함수 호출 비용**으로 실행됨.
* **차이점**: Exokernel은 **저수준 자원**에 대한 커널 검증을 캐시하는 성격이 강하고, SPIN은 **언어(모듈/타입) 수준의 경계 강제**로 **이름 해석·권한 범위**를 고정해 둔 뒤 **직접 호출**로 비용을 줄임.

#### 2) Visible revocation → (SPIN) Reclaim 이벤트로 협력적 회수
* 자원 회수가 필요할 때 **애플리케이션 측이 무엇을 반납할지 관여**하고, **자기 메타데이터를 동기화**하게 하는 절차.
* **Exokernel**: 커널이 회수를 요청하면 라이브러리 OS가 **반납 후보 선택** 및 **페이지 테이블 갱신**을 수행.
* **SPIN**: 물리 메모리 서비스가 **Reclaim 이벤트**를 발생시키면 확장/라이브러리 OS가 **대체 페이지 제안**이나 **매핑 정리**를 수행.
* **차이점**: 양쪽 모두 **협력적 회수**를 통해 **상태 불일치**를 줄이지만, SPIN은 이 과정이 **이벤트/핸들러 규약**으로 명문화되어 있고, **언어 안전성** 덕분에 **권한 범위 밖 접근**이 구조적으로 차단됨.

#### 3) Abort protocol → (SPIN) 강제 회수 + 시간 제한 + 선점 스케줄링

* 회수 요청에 **응답하지 않거나 지연**될 경우, 커널이 **일방적으로 바인딩을 끊고** 상위에 **복구 신호**를 전달하는 안전장치.
* **Exokernel**: **바인딩 강제 해제**, **repossession vector** 기록, **예외로 복구 유도**(앱 종료 없이 시스템 일관성 보전).
* **SPIN**: 신뢰된 코어 서비스가 **강제 회수/제한**을 수행하고, **시간 제한 핸들러**와 **글로벌 스케줄러 선점(Checkpoint/Resume)** 로 **오남용을 즉시 제어**.
* **차이점**: Exokernel은 **저수준 바인딩을 끊는** 프로토콜 중심, SPIN은 **핸들러 실행 시간·스케줄링 권한**으로 **행동 자체를 제한**하는 경향이 강함.

#### 4) Protected Control Transfer(PCT) → (SPIN) 도메인 간 보호된 인커널 호출

* **개념**: 보호 경계를 넘는 제어 이전에서 **원자적 도착**, **레지스터 보존**, **낮은 호출 비용**을 보장하는 메커니즘.
* **Exokernel**: **동기/비동기 PCT**로 **시간 조각 기부**와 **레지스터 기반 메시지**를 지원(μs급).
* **SPIN 대응**: **동적 링크된 도메인 간 호출**이 **함수 호출 비용**으로 수행되며, **언어·모듈 경계**가 보호 역할을 수행.
* **차이점**: Exokernel은 **커널↔유저 간 저비용 전환**을, SPIN은 **커널 내(공주소공간) 도메인 간 직접 호출**을 최적화한다는 점이 다름.

#### 5) Primitive hardware 노출 → (SPIN) 세분 서비스 인터페이스(조립식)

* 커널이 **저수준 자원**을 직접 노출할지, 혹은 **작게 쪼갠 서비스 인터페이스**를 제공해 **조합**하게 할지의 차이.
* **Exokernel**: **CPU, 물리 메모리, TLB, 예외/인터럽트, DPF 기반 NIC** 등 **원시 자원**을 **보안 다중화** 형태로 제공. 라이브러리 OS가 **모든 고급 정책**을 구성.
* **SPIN**: **Phys/Virt/Translation**(VM), **Strands**(스케줄링), 각종 **이벤트/핸들러** 등 **미세한 인터페이스**를 제공하여 **필요한 조합만 선택**해 인커널 확장을 구현.
* **차이점**: Exokernel은 **정책 전권을 사용자 공간(LibOS)** 에, SPIN은 **정책을 커널 내 안전 확장**으로 끌어와 **직접 호출 성능**과 **언어적 안전성**을 동시에 확보.

### 4. How Exokernel’s mechanisms meet the high-level goals

#### 확장성(Extensibility)

* 커널은 **저수준 원시(primitive)** 만 안전하게 다중화하고, **공유 서버를 지양**. 고수준 정책·기능은 **앱별 LibOS**에 위임
* **효과**: 애플리케이션은 **자기 목적에 맞는 VM/IPC/FS/스케줄러**를 자유롭게 설계·교체. 커널 인터페이스가 단순·안정적이므로 **실험·특수화**가 용이
* **예시**
  * 데이터베이스: **페이지 교체 정책**, **버퍼 고정(pinning)**, **로그 I/O 배치** 등을 LibOS 차원에서 최적화.
  * 통신 스택: **DPF(동적 패킷 필터)**를 내려 설치하여 **애플리케이션별 분류 규칙**을 적용(공유 서버의 고정 정책에 종속되지 않음).

#### 안전성(Safety)
* **Secure bindings + Capability**로 **권한 검증을 바인딩 시점**에 마치고, 사용 시에는 **값(태그) 확인만**으로 접근을 허용. **Visible revocation**으로 회수를 **명시적으로** 수행하고, 필요한 경우 **Abort**로 **강제 일관성** 회복.
* **효과**: 권한 없는 매핑·패킷·인터럽트는 **구조적으로 차단**. 회수 시 LibOS가 **자신의 메타데이터(예: 페이지 테이블)** 를 직접 정리하여 **상태 불일치**가 줄고, 비협조 상황에서도 **Abort**를 통해 **시스템 안정성**을 유지(앱 종료는 최후 수단).
* **예시**
  * 메모리 압박 시 커널이 **회수 요청**을 발행하면, LibOS가 **반납 대상**을 선택하고 더티 페이지는 **백스토어 기록** 후 **테이블 갱신**. 지연 시 **Abort-repossess**로 바인딩을 끊고 **복구 예외**를 통해 정합성 확보.

#### 성능(Performance)
* **빠른 예외 디스패치(업콜)**, **STLB 기반 TLB 용량 미스 흡수**, **PCT(보호된 제어 전달)**, **DPF(컴파일된 패킷 분류)**.
* **효과**: 권한 검증·경계 횡단·주소 변환·네트워크 분류의 비용을 **핫패스에서 최소화**. 결과적으로 **μs급 제어 이전**, **낮은 VM 오버헤드**, **고속 패킷 디멀티플렉싱**을 달성.
* **예시**
  * **STLB** 적중 시 업콜 없이 **즉시 TLB 재설치**, **PCT**로 **레지스터 보존·시간 기부**를 포함하는 **저오버헤드 IPC**, **DPF**로 **10–20×** 수준의 분류 가속.

### 5. How SPIN’s mechanisms meet the high-level goals

#### 확장성(Extensibility)
* **Event/Handler 모델**과 **커널 내 동적 링크**로 확장을 **커널 주소 공간에 co-locate** 시킴. **세분화된 서비스 인터페이스**(예: **Phys/Virt/Translation**(VM), **Strands**(스케줄링))를 제공해 **조립식 정책 구성**이 가능.
* **효과**: 확장은 **기본 구현을 대체·후킹**하거나 **세밀한 단위(페이지, 스레드 전환 등)** 에서 정책을 바꿀 수 있으며, **가드(guard)** 와 **실행 제약**(동기/비동기, 시간 상한, 순서)을 통해 **상황별 분기**가 가능. **타입 안전성** 덕분에 커널 내부 확장임에도 **안전하게** 운용됨.
* **예시**
  * 네트워크 경로에서 **패킷 도착 이벤트**에 핸들러를 등록하여 **프로토콜별 특수 처리**를 직접 구현.
  * VM에서 **Translation** 인터페이스의 **fault 이벤트**에 대응하여 **특정 페이지 캐시 정책**을 삽입.

#### 안전성(Safety)
* **Modula-3**의 **타입 안정성**, **인터페이스 강제**, **보호 도메인(네임스페이스)**, **Typed pointer capability**. **Export/Import 인가 콜백**으로 바인딩 시 **정책 검사**를 수행.
* **효과**: 확장 코드는 **허용된 인터페이스 범위 내에서만** 접근 가능하며, **위조·경계 침범**이 언어 수준에서 차단됨. 도메인 간 호출은 **정적·동적 링크 시점**의 약속에 기반하므로 **권한 범위가 명확**함. **시간 상한** 및 **선점형 스케줄러**로 **오남용 제어** 가능.
* **예시**
  * 확장이 커널 객체를 직접 참조하려면 **capability(타입드 포인터)** 가 필요하며, 링크 시 **인가 콜백**을 통과해야 함. 과도 실행 시 커널이 **Checkpoint/Resume**으로 **즉시 회수**.

#### 성능(Performance)
* **공주소공간 내 호출**(동일 커널 주소 공간), **동적 링크** 후 **직접 호출(프로시저 콜 비용)**, **이벤트 디스패처 최적화**(단일 핸들러·무가드 시 **직접 점프**).
* **효과**: 경계 횡단 비용이 **메시지 IPC나 트랩**에 비해 **극히 작아** 핫패스에서 **정책 세분화**가 가능. 다중 핸들러·가드가 있어도 **생성된 호출 경로**로 비용 최소화.
* **예시**
  * **Strands** 기반 스케줄링에서 **응답성 요구**에 따라 **앱 전용 스케줄러**를 얹더라도, 글로벌 스케줄러와의 상호작용이 **함수 호출 수준**으로 가볍게 유지.

## 개요
SPIN: 애플리케이션이 커널 내부에 들어와(co-location) 필요한 정책과 구현을 직접 교체/확장할 수 있게 설계한 OS

- 안전성: **Modula-3**(타입 안전 언어) 기반의 **language safety(타입 안전성)**, **protection domain(보호 도메인: 코드가 볼 수 있는 이름 공간)**, **event/handler binding(이벤트-핸들러 연결)**, **capability(권한 토큰: 위조 불가 타입 포인터)** 로 확보
- 성능: **커널 주소 공간에 동적 링크**해 **함수 호출 수준의 비용**으로 내려감

## 배경
### 문제
* 범용 OS는 모든 앱에게 **하나의 정책**만 제공
* **특수 앱**(예: DB, 실시간 미디어)은 **다른 정책**이 더 적합. 기존 구조에서는

  * 여러 번의 **system call/IPC**(커널 호출/프로세스 간 통신) 왕복이 필요하거나,
  * **안전하지 않은 C 커널 모듈**로 커널을 직접 수정해야 했음

### 목표
**범용성**을 유지하면서 **확장 가능**하고 **안전**하며 **빠른** OS

### 접근법
* **확장성:** 필요한 지점만 **event/handler**로 갈아끼우기
* **안전성:** **Modula-3 타입 안전성 + protection domain + capability**로 확장 권한을 엄밀히 제한
* **성능:** 확장을 **커널 주소 공간**에 **동적 링크**하여 **함수 호출 비용**으로 실행

### 개발자가 실제로 하는 일
1. 바꾸고 싶은 **커널 이벤트** 선택
2. **같은 타입**의 **핸들러** 구현(필요하면 **guard**(실행 조건)로 범위 좁히기)
3. 커널은 **domain + capability**로 권한을 제한하고, **직접 호출** 수준으로 호출 경로 최적화

## Design Pillars
1. **Co-location**: 확장 코드를 **커널 주소 공간**에 **동적으로 링크**
2. **Modula-3**: 컴파일러가 **인터페이스 경계**를 강제 → 인터페이스가 허용하지 않는 메모리/자원 접근 **불가**
3. **Logical protection domains**: 코드와 그 코드가 볼 수 있는 **내보낸 인터페이스 집합**으로 **커널 레벨 네임스페이스**(namespace: 프로그램이 이름(symbol)으로 참조할 수 있는 범위) 정의
4. **Dynamic call binding via events**: 페이지 폴트, strand 스케줄링, 패킷 도착 같은 시스템 동작을 **이벤트**로 모델링. 확장은 **핸들러를 등록**하고, 조건이 단순하면 **직접 호출**로 최적화

> * **커널(kernel)**: OS의 핵심 부분. 자원 관리·스케줄링 담당
> * **네임스페이스(namespace)**: 프로그램이 볼 수 있는 **이름/심볼의 범위**
> * **Modula-3**: **타입 안전성**과 **모듈 인터페이스**를 엄격히 강제하는 언어
> * **Capability**: **권한을 담은 위조 불가 타입 포인터**
> * **Event/Handler**: **이벤트**는 호출 지점, **핸들러**는 그 지점에서 실행될 사용자 구현

## Protection model
**목표:** **주소 공간 전환 없이**도 **정밀 권한 부여**와 **격리** 달성. 권한은 **타입 안전 인터페이스**를 통해서만 부여.

* **Address space(주소 공간)**: 실행 중인 프로그램이 볼 수 있는 **가상 주소 전체 범위**. 각 주소는 **페이지 테이블**로 물리 메모리에 매핑됨.
* **Namespace(네임스페이스)**: 프로그램이 **이름(symbol)** 을 붙이고 참조하는 **범위/집합**.

> SPIN의 핵심: **주소 공간은 공유**하지만 **네임스페이스는 분리**하여 안전 보장
> (즉, 같은 메모리를 보더라도, **무엇을 부를 수 있는지**가 엄격히 다름.)

### 구성 요소
#### 1) Capability

* 커널 자원(객체, 인터페이스, 인터페이스 집합)을 가리키는 **위조 불가 타입 포인터**로 표현
* **특정 인터페이스에 한하여** 정확히 그 권한만 부여
* **포인터 전달 = 권한 위임**

#### 2) Externalized references(외부화 참조)

* **비-타입-안전**인 사용자 공간으로 커널 참조를 내보낼 때는 **프로세스별 테이블 인덱스**로 전달
* 커널이 이 인덱스를 **다시 타입 안전 포인터로 복구**
* 인덱스는 **권한 범위**를 넘지 않음

#### 3) Protection domain(보호 도메인)

* **코드 + 그 코드가 볼 수 있는 심볼 집합**을 묶는 **언어 레벨 네임스페이스**
* 도메인은 **export/import 인터페이스**를 **명시**

#### 4) 신뢰된 in-kernel linker(커널 내 링커)

* 도메인 간 **import ↔ export**를 **동적 바인딩**
* **TCB**(신뢰 기반 컴퓨팅 베이스)의 일부로, **타입 검증**과 **정책 검사** 수행

### 도메인 수명 주기
* **Create**: 검증된 객체 파일로 **새 도메인 생성**
* **Resolve**: 한 도메인의 **import**를 다른 도메인의 **export**에 **연결** (이때 **타입/정책 검사**)
* **Combine**: **둘 이상의 도메인 네임스페이스를 합집합**으로 묶어 한 번에 보이게 함

### 권한 부여/검사
* **최소 권한(least privilege)**: 기본적으로 코드는 **자신이 import한 인터페이스**로만 커널 상태에 영향
* **export/import control**: **export하는 쪽**이 **권한 검사 콜백**을 등록 → **누가 어떤 조건에서** 가져갈 수 있는지 **바인딩 시점**에 정책 적용

### 호출 비용
* **주소 공간이 동일**하므로 **인터페이스 경계**를 넘어도 **trap/context switch 없음**
* 결과적으로 **procedure call(일반 함수 호출) 수준의 비용**

## Extension model
**목표:** 커널 동작을 **이벤트**로 외부화하고, 확장이 **핸들러**를 끼워 정책을 **교체/보강**. 이때 **타입 안전성 + 도메인 + capability**로 안전 보장.

### 이벤트
* 정의: **인터페이스가 export하는 모든 프로시저**
* 어떤 이벤트를 볼 수 있는지는 **도메인 네임스페이스 + capability**로 결정

### Handler 등록 lifecycle
* 핸들러는 해당 이벤트와 **정확히 동일한 타입**을 가져야 함
* `InstallHandler(event, handler, guard?, constraints?)`로 설치 (제거는 같은 키로 언바인딩)
* 각 이벤트의 **기본 구현 모듈**이 **설치/제거 승인 또는 거부**

### Guard
* 역할: **이벤트 인자/상태**를 검사해 **일부 경우에만** 핸들러 실행
* 구성: 여러 조건의 **AND**로 구성(필요 시 **OR** 지원)

  * 예: `proto == UDP && dstPort == 9000`
* **IP 모듈**은 패킷 헤더의 **protocol type**을 guard로 생성해 **프로토콜별 핸들러 분리**
* **가드가 없고 핸들러가 한 개면 → 직접 호출**, 여러 개여도 **생성된 분기 코드**로 빠르게 평가

### Constraints
* **동기/비동기**

  * **동기**: 호출자 스택에서 즉시 실행(지연 짧음, **핫패스** 적합)
  * **비동기**: 별도 스레드에서 실행(긴 계산/IO **격리**)
* **Time bound(최대 실행 시간)**: 기본 모듈이 **최대 실행 시간**을 지정, **초과 시 중단**하거나 **비동기 전환**
* **Ordering(순서)**: 여러 핸들러가 있을 때 **실행 순서 지정**, 충돌 시 **기본 모듈 규칙**을 따름
* 커널은 **선점형**이므로 어떤 핸들러도 **CPU 독점 불가**

> * **핫패스(hot path)**: 자주, 빠르게 지나가는 핵심 실행 경로
> * **선점형(preemptive)**: 커널이 필요하면 실행 중인 작업을 **중간에 끊고** 다른 작업으로 전환할 수 있음

## 확장 가능한 핵심 서비스
### 1) Virtual Memory(가상 메모리) 분해 인터페이스

* **PhysAddr**: 물리 페이지 **관리**(할당/해제), **reclaim 이벤트**(회수 요청) 발행
* **VirtAddr**: 가상 주소 **범위 할당**, **주소/길이/ASID**(주소 공간 식별자) 포함 **capability 제공**
* **Transition**: **매핑 컨텍스트 생성** 및 **Add/Remove mapping**, 폴트 이벤트 **`BadAddress / PageNotPresent / ProtectionFault`** 발생

### 2) Thread and Strands

* **Strand**: 커널이 노출하는 **스케줄링 단위**(이름만 있고 필수 커널 상태 없음 → **경량 실행 문맥**)
* **Strand 인터페이스 이벤트**

  * **Block/Unblock**: 드라이버/인터럽트가 요청하는 **실행/비실행 가능 전환**
  * **Checkpoint/Resume**: 스케줄러와 스레드 패키지가 **실행 상태 저장/복원**
* **LibOS** 활용

  * **strands 위에 자체 thread package/scheduler 구현**(1:1 또는 M\:N)
  * **런 큐**, **TCB**(스레드 제어 블록), **strand별 메타데이터**, **동기화 구조** 유지
  * **resume**을 받으면 자체 런 큐를 돌려 **thread dispatch**, **checkpoint**를 받으면 상태 저장 후 **CPU 양보**

## How SPIN prevents resource hogging
### CPU 과점 방지
* 최종 권한자는 **global scheduler**(전역 스케줄러). 어떤 앱 스케줄러든 **checkpoint**로 즉시 중단 가능, **resume**을 받아야만 실행
* **time-bound handlers**: 기본 모듈이 **시간 제한** 또는 **비동기 처리**를 강제 → **장시간 작업**은 중단/off-loading
* **global CPU 정책**은 **신뢰된 코드**만 교체 가능(앱이 임의로 시스템 정책 변경 **불가**)
* **초기 매크로 정책 예시**: 특정 LibOS의 **scheduler strand**에 **우선순위/가중치** 부여 → **strand 수 제한** → **time slice** 할당 → 앱이 **global policy**를 임의로 교체하지 못함

### Physical memory 과점 방지
* **Capability 범위 할당**: LibOS는 **보유 capability** 안에서만 할당 가능
* **Reclaim 이벤트**: 물리 메모리 서비스가 언제든 **회수 요청**을 보낼 수 있음.

  * 핸들러가 **대체 페이지**를 제시할 수 있으나, **대상 페이지의 매핑은 무효화**
* **초기 매크로 제어**: 각 LibOS에 **페이지 예산**을 부여. **신뢰된 할당자**가 **성장 승인** 여부 결정 → **Reclaim**이 시스템 전체 **메모리 압력**을 집행 → 어느 하나의 LibOS도 다른 OS를 **RAM 기아 상태**로 몰아가지 못함

* **VM**: **PhysAddr**, **VirtAddr**, **Transition**, **Fault 이벤트**, **Reclaim** 포함
* **Threads**: **Strand**, **Block/Unblock/Checkpoint/Resume**, **Global scheduler 우선 구조**

## 1. 동기 (Synchronous) vs. 비동기 (Asynchronous)
### 동기 (Synchronous)
**작업을 하나씩 순차적으로 처리**하는 것입니다.
한 작업이 끝나야지만 다음 작업을 처리할 수 있습니다.

이는 요리를 할 때 한 요리가 완성될 때 까지 다음 요리를 시작하지 않는 것과 비슷합니다.

```python
import time

  def boil_water():
      print("물 끓이는 중...")
      time.sleep(3)  # 3초 동안 물을 끓입니다.
      print("물 끓음!")

  def make_tea():
      print("차 우려내는 중...")
      time.sleep(2)  # 2초 동안 차를 우려냅니다.
      print("차 완성!")

  def main():
      # 순차적으로 실행: 물을 끓이고 그 후 차를 만듭니다.
      boil_water()
      make_tea()

  main()
```
이 방식에서는 물 끓이기가 끝나야 차 만들기를 시작할 수 있으므로, 전체 시간이 5초(3초 + 2초) 걸립니다.

### 비동기 (Asynchronous)
**작업을 동시에 처리**할 수 있고, 특정 작업을 진행하는 동안 다른 작업도 병행할 수 있습니다.

요리할 때, 물이 끓는 동안 다른 반찬을 준비하는 것과 같습니다.

```
import asyncio

async def boil_water():
    print("물 끓이는 중...")
    await asyncio.sleep(3)  # 3초 동안 기다리지만, 이 시간에 다른 작업을 수행할 수 있습니다.
    print("물 끓음!")

async def make_tea():
    print("차 우려내는 중...")
    await asyncio.sleep(2)  # 2초 동안 기다리지만, 동시에 다른 작업이 가능합니다.
    print("차 완성!")

async def main():
    # 두 작업을 동시에 실행합니다.
    await asyncio.gather(boil_water(), make_tea())

asyncio.run(main())
```
이 경우, 두 작업이 동시에 진행되므로 전체 실행 시간은 가장 긴 작업인 3초 정도로 줄어듭니다.

## 2. Blocking vs. Non-Blocking
### Blocking
어떤 **작업이 완료될 때까지 프로그램의 진행이 멈추고**, 다른 작업을 수행하지 못하는 상태입니다.

우체국에서 한 사람씩 창구에서 업무를 처리하는 것처럼, 한 사람이 업무를 마칠 때까지 다음 사람이 대기하는 상황과 비슷합니다.

```
import time

print("처리 시작")
time.sleep(2)  # 이 동안 프로그램은 아무 작업도 못합니다.
print("처리 완료")
```

### Non-Blocking
작업 요청 후, 그 **결과를 기다리지 않고 바로 다른 작업을 진행**할 수 있는 방식입니다.

자동 발권 기계처럼, 티켓을 구매하는 동안에도 다른 일을 할 수 있는 상황과 비슷합니다.

```
import asyncio

async def non_blocking_example():
    print("처리 시작")
    await asyncio.sleep(2)  # 이 시간 동안 이벤트 루프가 다른 작업들을 처리할 수 있습니다.
    print("처리 완료")

asyncio.run(non_blocking_example())
```
여기서는 2초의 대기 시간이 있지만, 그 동안 다른 비동기 작업을 동시에 실행할 수 있으므로 프로그램 전체가 멈추지 않습니다.

#### 이벤트 루프
이벤트 루프는 비동기 작업들을 관리하고, 예약된 작업들을 순서대로 실행하는 **중앙 관리 시스템**입니다.

요리로 비유해보면 주방장의 역할과 같습니다. 주방장은 각 요리의 상태를 확인하고, 준비가 완료되면 즉시 다음 작업을 실행하게 합니다.

## 마무리
아마 동기와 blocking의 차이, 비동기와 non-blocking의 차이에 대해 헷갈릴 수 있을 것 같습니다.

실제로 동기 방식의 코드에는 보통 blocking 호출이 함께 사용되기 때문에 두 개념이 같이 나타나지만, 쉽게 말하면 **동기**는 **작업의 처리 순서**에 관한 개념이고, **blocking**은 **실행이 중단되는 상황**을 설명합니다.

- 동기: 먼저 A 작업을 수행한 후, 그 다음에 B 작업을 수행
- Blocking: 특정 작업이 완료될 때까지 다음 작업이 실행되지 않는 상태

비동기와 non-blocking을 잘 활용하면 I/O 작업 중에도 다른 작업을 수행할 수 있어 자원을 효율적으로 사용할 수 있으며, 여러 요청을 동시에 처리할 수 있기 때문에 동시 접속자가 많을 때 성능이 향상됩니다.

CAP Theorem은 분산 시스템이 **동시에 만족시킬 수 없는** 세 가지 특성입니다.

### 1. Consistency
Consistency는 분산 시스템에 있는 **모든 노드가 같은 시점에 동일한 데이터**를 갖도록 보장하는 특성입니다.

쉽게 말하면, 한 은행 지점에서 입금을 하고, 다른 지점에 방문했을 때도 즉시 동일한 잔액을 확인할 수 있어야 하는 상황을 의미합니다.
만약 A에서 입금을 했는데 B 지점에서는 반영되지 않아 잔액이 다르다면, 이는 일관성(consistency)이 보장되지 않는 상태입니다.

### 2. Availability
Availability는 **시스템이 항상 응답을 제공할 수 있는 능력**을 뜻합니다.

만약 시스템 일부에 장애가 발생하더라도 여전히 서비스가 지속되어 요청에 대해 항상 응답을 제공해야 합니다.

예를 들어 카페에 방문했을 때, 한 손님이 커피를 주문했는데 어떤 이유로 카페에서 커피를 제공하지 못한다면 그 카페는 가용성이 낮다고 볼 수 있습니다.

다르게 말해, 어떤 이유로 커피가 늦어지더라도 나중에라도 커피를 제공하는 것처럼 반드시 응답(정상적인 응답 혹은 오류메시지라도) 받아야 한다는 점이 있습니다.

### 3. Partition Tolerence
Partition Tolerence는 **시스템 네트워크의 일부 구간이 끊기는 일이 발생하더라도 시스템이 정상적으로 작동하는 능력**을 의미합니다.

예를 들어, 한 도시의 도로에 공사가 진행되어 통행이 불가능한 상태일때도 다른 우회도로를 통해 조금 오래 걸리더라도 차량 간 이동이 가능한 상황을 생각해 보시면 됩니다.

분산 시스템에서는 복제 노드를 만들어서 사용자에게 응답할 수 있도록 처리할 수 있습니다.

### 정리
CAP Theorem은 위 세 가지 특성 중에서 두 가지만을 동시에 완벽하게 만족시킬 수 있다는 이론입니다.

보통 네트워크 장애(Partition)를 완전히 배제하는 건 불가능하기 때문에 보통 Consistency와 Availability 사이에서 하나를 희생해야만 합니다.

MongoDB는 **CP(Consistency + Partition Tolerence)** 를 따르는데, 만약 primary node에 문제가 생겼다면 secondary(복제된) 노드 중 하나가 primary로 promote 되어야 합니다.
이 때, 새로운 primary 노드가 생기는 동안 **모든 쓰기 작업은 사용 불가능한 (NOT available) 상태**가 되므로 MongoDB는 CP system이라고 볼 수 있습니다.

예를 들어, 특정 서비스에서 복잡한 연산 때문에 한 개의 메시지를 처리하는 데 시간이 너무 오래 걸린다면, 멀티 프로세싱 기법을 도입하여 문제를 해결할 수 있습니다. 또한, 한 서비스가 다른 서비스의 네트워크 응답을 기다려야 하는 상황에서는, 멀티 스레딩을 활용하여 대기 시간 동안 다른 작업을 병행할 수 있습니다.

이 글에서는 멀티 프로세싱과 멀티 스레딩의 차이가 무엇인지, 그리고 이 방법들을 파이썬에서 어떻게 사용할 수 있을지 알아보도록 하겠습니다.

## 멀티 프로세싱
먼저, 프로세스의 개념에 대해서 알아보겠습니다.

**프로세스**: **컴퓨터에서 실행 중인 하나의 프로그램**이라고 생각하면 됩니다. 예를 들어, 웹 브라우저, 미디어 플레이어 등이 각각 하나의 프로세스입니다.

각 프로세스는 운영체제로부터 독립된 메모리 공간(힙, 스택 등)과 자원을 할당 받고, 한 프로세스에 문제가 발생해도 다른 프로세스에는 영향을 주지 않습니다.

CPU 코어를 활용해 위와 같은 여러 개의 프로세스들을 병렬로 실행할 수 있으며, 프로세스 간 통신은 **IPC**(Inter-Process Communication)을 사용합니다.
예를 들어, 한 컴퓨터에서 웹 브라우저와 미디어 플레이어를 동시에 실행하는 경우, 두 개의 독립된 프로세스가 작동합니다.  

아래는 Python에서 multiprocessing을 구현할 수 있는 간단한 예제입니다.
```python
from multiprocessing import Process
import time

def process_file(file_name):
    print(f"[프로세스] {file_name} 처리 시작")
    # 실제 파일 처리는 생략하고, 2초간 대기합니다.
    time.sleep(2)
    print(f"[프로세스] {file_name} 처리 완료")

def main():
    files = ['file1.csv', 'file2.csv']
    processes = []

    # 각 파일에 대해 별도의 프로세스를 생성합니다.
    for file in files:
        p = Process(target=process_file, args=(file,))
        processes.append(p)
        p.start()  # 각 프로세스 시작

    # 모든 프로세스가 끝날 때까지 대기합니다.
    for p in processes:
        p.join()

    print("모든 프로세스 작업 완료")

if __name__ == "__main__":
    main()
```
#### 동시에 실행할 수 있는 프로세스의 수
그럼, **동시에 실행되는 프로세스의 수**는 어떻게 결정하는 것이 좋을까요?


보통 **CPU bound** 작업일 경우, 일반적으로 **실행할 프로세스의 수를 CPU 코어 수와 동일**하게 맞추는 것이 좋습니다. 예를 들어, 8코어 시스템에서는 8개의 프로세스를 동시에 실행하면 각 프로세스가 별도의 코어에서 동작하며 최적의 성능을 낼 수 있습니다.

만약 작업이 **I/O bound**일 경우, CPU 사용률이 낮으므로 **CPU 코어 수보다 더 많은 프로세스**를 실행해도 문제가 없을 수 있습니다. 하지만 동시에 실행되는 프로세스가 많아지면, 각 프로세스가 사용하는 메모리와 자원에 대한 부담이 커지기 때문에 시스템의 **메모리 용량**과 **자원 사용량**을 고려하여 정해야 합니다.

#### IPC (Inter-Process Communication)
IPC, 프로세스 간 통신은 서로 독립적으로 실행되는 여러 프로세스들이 데이터를 주고받을 수 있도록 해주는 메커니즘입니다.

**IPC 방법들**
1. **Pipe와 FIFO (Named Pipe)**  
    **파이프**: 두 프로세스 간에 데이터를 일방향으로 전달하는 통신 채널입니다. 보통 부모/자식 프로세스 사이에서 사용됩니다.  
    **FIFO (Named Pipe)**: 이름이 있는 파이프로, 관련 없는 독립적인 프로세스들 간에도 통신할 수 있습니다.
2. **메시지 큐**  
  여러 프로세스가 데이터를 메시지 단위로 보내고 받을 수 있는 큐입니다.
  메시지는 순서대로 저장되고, 한 프로세스가 메시지를 보내면 다른 프로세스가 이를 꺼내어 처리합니다.
3. **공유 메모리**  
  여러 프로세스가 같은 메모리 영역에 접근할 수 있게 하는 방법입니다.
  접근 속도가 매우 빠르지만, race condition(동기화 문제)를 해결하기 위한 추가 메커니즘이 필요합니다.
4. **소켓**  
  네트워크를 통해 프로세스 간 통신을 할 수 있고, 동일 컴퓨터 내의 프로세스 뿐만 아니라 다른 컴퓨터의 프로세스와도 통신할 수 있습니다.

파이썬에서는 사용의 편의성과 안정성 면에서 메시지 큐(`multiprocessing.Queue`)가 가장 널리 사용됩니다. 

#### 멀티 프로세싱 풀 (Pool)
멀티 프로세싱 풀은 미리 정해진 수의 프로세스(작업자)를 생성해두고, 이를 통해 작업을 분산하여 실행하는 방식입니다. 이렇게 하면 매번 새로운 프로세스를 생성하는 오버헤드를 줄일 수 있어, 다수의 작업을 효율적으로 처리할 수 있습니다.

**작동 원리**
1. 풀은 시작할 때 **지정한 수의 프로세스를 미리 생성**합니다. 예를 들어, **CPU 코어 수나 작업량**에 맞게 4개, 8개 등의 프로세스를 만들어 둡니다.
2. 여러 작업을 풀에 제출하면, 풀에 있는 프로세스들이 작업을 나눠서 실행합니다. **작업이 끝난 프로세스는 다시 대기** 상태로 돌아가 다음 작업을 처리할 준비를 합니다.
3. 한 번 생성된 프로세스는 여러 작업에 대해 **재사용**됩니다.

## 멀티 스레딩
**스레드**: 스레드는 하나의 프로세스 내에서 **실제로 작업을 수행하는 작은 실행 단위**입니다. 즉, 하나의 프로세스 안에서 여러 가지 일을 동시에 진행할 수 있도록 도와주는 역할을 합니다. 예를 들면, 크롬(프로세스)에서 여러 개의 탭마다 웹사이트를 불러오는 작업은 멀티 스레딩으로 이루어집니다.

같은 프로세스 내의 스레드들은 **모두 동일한 메모리(데이터, 변수 등)를 공유**하며, 스레드들끼리 데이터를 쉽게 주고받을 수 있습니다. 하지만, 동시에 **같은 데이터에 접근하다 보면 서로 충돌**할 수도 있어 주의해야 합니다.

#### Python에서 멀티 스레딩과 GIL (Global Interpreter Lock)
Python의 가장 널리 쓰이는 interpreter인 CPython에는 **GIL**이라는 메커니즘이 있습니다. GIL은 한 번에 **오직 하나의 스레드**만 Python 코드를 실행하도록 하는 잠금장치입니다.


Python은 **Garbage collection**을 사용해 메모리를 자동으로 관리합니다. GIL은 **여러 스레드가 동시에 메모리를 변경하는 일을 방지**하고, 프로그램이 복잡해져도 메모리 관리가 안전하게 이루어지도록 도와줍니다.

하지만, GIL으로 인해 여러 스레드를 사용해도 한 시점에 오직 하나의 스레드만이 실제로 코드를 실행합니다. 따라서, 복잡한 계산이나 **CPU를 많이 사용하는 작업(CPU bound)은 여러 스레드로 병렬 처리했을 때 기대만큼의 성능 향상을 얻기 어렵습니다**.

반면에, 파일 입출력, 네트워크 통신 등과 같이 **기다리는 시간이 상대적으로 많은 작업**(I/O bound)들에서는 **스레드가 대기 상태로 있을 때 다른 스레드가 실행**될 수 있으므로 GIL의 영향이 덜합니다. 이 경우, CPU는 한 스레드에만 국한되지 않고 다른 스레드로 전환되어 작업을 진행합니다.

예를 들면, 파일을 읽거나 쓸 때, CPU는 집중적으로 계산하는 것이 아니라, 외부 장치(디스크 등)와 데이터를 주고받느라 기다리는 시간이 발생합니다. 이 때 스레드가 **대기 상태**로 들어가면서 GIL을 해제하게 됩니다. 이로 인해 다른 스레드들이 CPU를 사용할 수 있게 되어, 여러 파일을 동시에 읽거나 쓸 수 있습니다.
  
엄밀히 말하면 CPU가 여러 작업을 번갈아 실행하기 때문에, 동시에 실행되는 것처럼 보이지만 실제로는 **컨텍스트 스위칭**이 계속 발생하며 작업을 처리합니다.

CPython에서는 GIL이 interpreter의 핵심 설계 요소이기 때문에 Python 자체에서 **GIL을 완전히 해제하거나 제거하는 것은 불가능**합니다.

#### 동시에 실행할 수 있는 스레드의 수
멀티 스레딩에서 **동시에 실행할 수 있는 스레드의 수**는 작업의 종류에 따라 달라집니다.

**CPU 집약적인 작업**의 경우, CPython의 GIL 때문에 한 번에 한 스레드만 Python 바이트코드를 실행합니다. 따라서, CPU 코어 수에 맞춰 스레드를 구성하는 것이 좋습니다. 이렇게 하면 불필요한 스레드 전환(컨텍스트 스위칭) 오버헤드를 줄일 수 있습니다.

반면, **I/O 바운드 작업**처럼 파일 입출력이나 네트워크 요청과 같이 대기 시간이 긴 작업에서는, CPU 사용이 크게 발생하지 않으므로 CPU 코어 수보다 훨씬 많은 스레드를 사용할 수 있습니다. 예를 들어, 네트워크 요청이 많은 애플리케이션에서는 수십 개 이상의 스레드를 사용해도 오히려 성능 향상을 기대할 수 있습니다.

#### 멀티 스레딩에서의 풀
멀티 프로세싱에서 풀을 사용하는 것과 같이, 스레딩에서도 풀 개념을 적용할 수 있습니다. Python에서는 주로 `cuncurrent.futures.ThreadPoolExecutor`를 사용하여 풀을 구성합니다. 이를 통해 **미리 정해진 수의 스레드를 생성하고, 작업을 해당 스레드들에 분산**시켜 실행할 수 있습니다.

## 가비지 컬렉션 (Garbage Collection)
Python의 가비지 컬렉션은 메모리 관리를 자동으로 수행하는 메커니즘입니다. 이 메커니즘은 크게 두 가지 방법을 사용합니다.
### 1. 참조 카운팅 (Reference Counting)
어떤 물건을 여러 사람이 공유하고 있을 때 몇 명이 그 물건을 사용 중인지 숫자로 세어보는 것과 비슷합니다.

**작동 원리**
1. Python에서 어떤 데이터를 저장하는 객체(list, dictionary, etc)가 만들어지면 이 객체를 사용하고 있는 변수가 몇 개인지 기록합니다.
2. 만약 변수가 그 객체를 사용하면 숫자가 1 증가하고, 더 이상 사용하지 않게 되면 숫자가 1 감소합니다.
3. 이 **참조 카운트가 0**이 되면 그 객체는 아무도 사용하지 않는 것으로 판단되어 청소부가 그 객체를 메모리에서 제거합니다.
```python
a = [1, 2, 3]    # 리스트 객체 생성 (참조 카운트 증가)

b = a            # b가 a를 참조 (참조 카운트 증가)

del b            # b 삭제 (참조 카운트 감소)
```
### 2. 순환 가비지 컬렉터 (Cyclic Garbage Collector)
때로는 두 개 이상의 객체가 서로를 참조하면서 **서로를 잡아먹는** 상황이 생깁니다. 예를 들어, A가 B를, B가 A를 참조하고 있으면 외부에서는 둘 다 사용하지 않더라도 참조 카운트가 0이 되지 않습니다.

```python
class A:
    def __init__(self):
        self.other = None

# 두 객체 생성 후 서로를 참조하게 만듭니다.
a = A()
b = A()
a.other = b  # a는 b를 참조
b.other = a  # b는 a를 참조

# 외부 참조 제거
a = None
b = None

# 이제 두 객체는 외부에서 접근할 수 없지만 서로를 참조하므로 참조 카운트는 0이 되지 않습니다.
```
Python은 이러한 순환 참조 문제를 해결하기 위해 정기적으로 청소를 하는 **순환 가비지 컬렉터** 시스템을 사용합니다. 이 시스템은 주기적으로 객체 그래프를 탐색하여, **외부에서는 접근할 수 없지만 내부적으로 서로 참조하는 객체들**을 찾아냅니다.
#### 세대 개념
객체는 **얼마나 오래 살아남았느냐**에 따라 몇 개의 세대로 분류됩니다. 최근에 생성된 객체는 0세대, 조금 오래된 객체는 1세대, 가장 오래된 객체는 2세대로 분류됩니다.

이렇게 세대를 구분하는 이유는 대부분의 객체가 짧은 수명을 가지고 있고, 오래 살아남은 객체는 변경 가능성이 낮다고 판단하여 더 자주 검사하지 않음으로써 가비지 컬렉션 오버헤드를 줄이기 위함입니다.

### 고려 사항
한 객체를 참조하는 수가 많을 경우 **참조 카운트를 업데이트하는 오버헤드**가 발생할 수 있습니다. 객체에 대한 참조를 추가하거나 제거할 때마다 메모리 내에서 해당 값을 읽고, 수정하고, 다시 저장하는 작업이 필요합니다. 
이런 연산이 반복되면 단순히 그 객체를 사용하거나 해제하는 비용 외에도 참조 카운트 업데이트에 따른 부가적인 CPU 연산 비용이 누적될 수 있습니다.

예를 들어, 수천 개의 복잡한 데이터 구조에서 한 객체가 여러 부분에서 참조될 경우, 참조 카운트 관리에 드는 시간이 전체 성능에 영향을 줄 수 있습니다.

OS는 새로운 메모리 블록을 할당하거나, 사용이 끝난 메모리 블록을 해제할 때 **시스템 호출**을 사용합니다. 이러한 호출은 사용자 코드에서 직접 호출하는 연산보다 훨씬 느리고 오버헤드가 큽니다.


또한, 메모리 할당/해제를 반복하면 메모리 내부에 작고 산발적인 빈 공간들이 생기는데, 이를 **메모리 단편화**(Fragmentation)라고 합니다. 단편화가 심해지면 **메모리 사용 효율이 떨어지고 큰 연속된 메모리 공간을 할당받기 어려워집니다**.


이와 같이 메모리 할당 및 해제는 비용이 크므로 Python은 **메모리 풀**과 같은 기법을 통해 메모리를 재활용합니다. 메모리 풀은 **미리 일정 크기의 메모리 블록들을 할당해 놓고 필요할 때마다 이 블록들을 재활용**하는 방식입니다.

예를 들어, CPython은 짧은 문자열이나 작은 리스트와 같은 소형 객체를 위한 전용 메모리 할당기를 사용합니다. 이 풀은 **한 번에 시스템으로부터 큰 메모리 블록**을 받아 내부에서 작고 고정된 크기의 블록들로 나눈 후, 객체 생성 시 이 블록들을 할당합니다.

이 방식을 사용하면 새로운 객체를 만들 때마다 OS에 매번 메모리 할당 요청을 보내지 않아도 되므로 **매우 빠르게 메모리를 할당**할 수 있습니다. 객체가 해제되면 해당 메모리 블록은 즉시 운영체제에 반환되지 않고 **메모리 풀에 다시 저장**되어 다음에 **재사용**됩니다.


만약 현재 **할당된 메모리 풀이 모두 사용중**이라면:
1. Python의 메모리 할당기는 OS에 추가 메모리를 요청합니다.
2. 운영체제에서 추가 메모리를 제공하면 메모리 풀은 확장되어 이후에 새로운 객체 할당에 사용됩니다.
3. 만약 운영체제에서 더 이상 메모리를 제공할 수 없다면 Python은 더 이상 객체를 위한 메모리를 할당할 수 없게 됩니다. (`MemoryError` Exception 발생)

메모리 풀 확장 시 여러 프로세스가 동시에 메모리를 요구할 수 있고 이런 상황에서는 경쟁이 발생할 수도 있습니다.
