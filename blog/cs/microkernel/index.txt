# μ-Kernel

## 개요
* 초창기 마이크로커널이 느리고 경직되어 보였던 이유는 개념 자체의 한계가 아니라, **커널이 과도하게 비대**했고 **하드웨어 특성을 살리지 못한 구현** 때문
* 해결책: **커널에 ‘불가피한 메커니즘’만 남기는 것**. 즉, 보호와 자원 다중화를 위한 **최소 추상**만 커널에 두고, 정책·고급 기능은 모두 사용자 공간으로 내림

## μ-커널의 최소 API
1. **주소공간(Address Space)** + **세 연산**
   * **grant(양도)**: 페이지 소유권을 다른 주소 공간으로 넘김(보낸 쪽 매핑 제거). 중간 페이저가 끼어도 소유권 경로가 단순해지고 내부 매핑이 불어나지 않음.
   
   * **map(공유)**: 보낸 쪽에도 매핑을 유지한 채 **공유 매핑**을 만듦. 공유 메모리, CoW 같은 패턴을 사용자 공간에서 구현.
   
   * **flush(제거)**: 자신의 주소 공간 안에서 특정 매핑을 제거하고, 그 매핑에서 파생된 하위 매핑도 연쇄적으로 무효화. 타인의 매핑은 제거할 수 없으니 보호 보장.
   
   * **I/O 권한 일원화**: 메모리-맵드 I/O·포트 접근도 페이지 단위 권리로 관리(메모리와 동일한 규율로 **grant/map/flush**).
> 구현 관점: 물리 프레임마다 “매핑 트리”를 두어 어떤 주소 공간·가상 페이지가 그 프레임을 참조하는지 지역적으로 기록하면 grant/map/flush가 빠르고 안전해짐.

2. **스레드(Thread)**
   * 특정 주소 공간에 결박된 실행 컨텍스트. 
   * 스레드 전환은 종종 주소 공간 전환을 수반하므로, 커널이 주소 공간 무결성과 관련된 상태 변화를 엄격히 통제.

3. **IPC(프로세스 간 통신)**
   * **메시지 기반 통신**을 기본 원시로 두고, 이것으로 RPC 같은 상위 추상 구성.
   * **인터럽트를 IPC로 모델링**하면, 드라이버도 사용자 공간에서 만들 수 있음 (커널은 장치 의미에 관여하지 않고, 인터럽트는 특정 ID의 “빈 메시지”로 전달).

4. **UID(고유 식별자)**
   * 스레드·태스크·채널을 **공간·시간 전역**에서 확실하게 구분하는 값. 로컬 통신에 과한 암호학 대신, **커널이 싸게 제공하는 UID**가 실용적임.

## 왜 이 네 가지면 충분한가? (유연성의 실증)
* **유저 수준 페이저/메모리 관리자**: 일반 VM부터 데이터베이스 특화 매핑까지 정책을 자유롭게 설계·합성할 수 있음 (겹겹이 쌓는 “스택형” 구성도 자연스럽게 가능).
* **드라이버** : 장치 레지스터를 매핑하면 **순수 사용자 프로세스**로 구현됨 (부트 단계만 예외적으로 도와주고 이후 제거).
* **네트워크/원격 통신**: IPC 서버가 네트워크 프로토콜을 로컬 IPC처럼 제공하고, 공유 버퍼는 map으로 전달
* **UNIX 성격**: **페이저 + IPC 서버 조합**으로 전통적 OS 성격도 위에서 구현할 수 있음.

## 성능
* **커널 ↔ 유저 전환**은 하드웨어가 제공하는 최저치에 근접하도록 만들 수 있음. 과거의 큰 비용은 커널 내부 경로가 비대해서 생긴 현상
* **주소 공간 전환**의 진짜 비용은 “전환”이라는 개념 자체보다 **TLB 구조와 재적재 방식**에 달려 있음. 적절한 설계로 매우 낮은 수준까지 줄일 수 있음.
* **IPC**도 경로 다이어트와 작업셋 관리만 잘하면 짧은 지연으로 구현됨. **인터럽트를 메시지로 처리**하는 구조가 실용적일 만큼 충분히 빠르게 만들 수 있음.
* **캐시/TLB 간섭**은 정렬·배치·재적재 최소화 같은 구현 기술로 상당 부분 억제할 수 있음

## 프로세서 의존성(“커널 자체 이식성”의 재해석)
* 효율 좋은 μ-커널은 트랩·TLB·세그먼트·캐시 같은 CPU 디테일에 맞춘 설계가 필수 (아키텍처별로 달라져야 함)
* **그 위에 얹힌 시스템(서버·라이브러리)** 의 이식성은 그대로 유지

## 관련 작업과 포지셔닝
* **Synthesis**: 커널 경로 특수화를 위해 동적 코드 생성을 썼지만, 현대 CPU에서는 코드 팽창·I-캐시 압력 문제가 큼.
* **SPIN**: 언어 기반 보호로 커널 내부 확장을 허용해 경계 횡단을 줄이지만, 커널 모드 실행과 주소 공간 효과는 남음. 컴파일러 기술과 μ-커널의 결합이 유망.
* **Mach 변종들**: IPC 의미론을 조정했지만 최소 μ-커널 경로 대비 여전히 무거움.
* **Exokernel**: 저수준 다중화를 직접 노출해 매우 빠른 보호된 제어 이전을 보여줌(대신 인터페이스가 아키텍처에 더 민감).

## 결론
* **최소 메커니즘**(주소공간 grant/map/flush, 스레드, IPC, UID)만으로 **임의의 OS 성격**을 위에 구축 가능
* 성패는 **적절한 추상 선택**과 **대상 CPU에 맞춘 경로 설계**, **실측 기반 튜닝**에 달려 있다. 공개된 **L4**가 실험 기반을 제공

# Improved Address-Space Switching on Pentium

## 문제: Untagged TLB의 전환 비용
486/Pentium 등 **ASID 없는(TLB에 주소공간 태그가 없는)** CPU에서는 주소 공간 전환 시 **CR3 교체 → TLB 플러시**가 일어나고, 이후 **TLB 리필**이 전체 비용을 지배함. 

TLB가 클수록 더 아픔.

## 해법(세그먼트 기반 “small-space” 멀티플렉싱)
* **여러 개의 `작은 사용자 공간(small spaces)`** 을 하나의 사용자 선형 공간 내부에 공존시키고,
* 전환 시 **CR3는 건드리지 않은** 채, 사용자 평면 세그먼트의 **base/limit(디스크립터)만 수정**해 다른 작은 공간을 가리키게 만듦
* 사용자 입장에서는 **같은 세그먼트 선택자를 계속 쓰므로 완전 투명**하고, μ-커널 API도 바꿀 필요가 없음.

## 메모리 배치와 전환 분기(개념)
* 사용자 주소 공간을 **일반적인 `큰 공간` 영역**과 **모든 태스크가 공유하는 `작은 공간 창`** , 그리고 **커널 영역**으로 나눔 (정확한 비율은 중요치 않음).
* **전환 분기**
  * **Large→Large(서로 다른 태스크)**: 기존 방식대로 **CR3 교체(플러시 불가피)**
  * **Large→Small / Small→Small / Small→직전 Large**: CR3는 유지, 디스크립터만 갱신 후 데이터 세그먼트 레지스터를 리로드하여 새 base/limit을 반영

## IPC 경로와 복사 경로 최적화
* 커널은 진입 시 커널 전용 세그먼트로 전환해 안전을 확보한 뒤, 대상이 작은 공간 경로면 **디스크립터 갱신 + 세그먼트 리로드**만 하고 사용자로 복귀
* **복사 최적화**: 작은 공간 창 덕분에 송·수신 버퍼가 커널에서 동시에 보이는 구성이 가능 -> **임시 매핑 없이 바로 복사** 가능.

## 동적 분류와 압력 대응(자동·투명)
* 상단 사용자 영역을 쓰지 않는 태스크는 자동으로 작은 공간으로 분류됨. 이후 상단을 매핑하면 **큰 공간으로 승격**됩
* 작은 공간 슬롯이 부족하면 휴면 중인 **작은 공간들을 큰 공간으로 되돌려 슬롯 회수**
* 이 모든 과정은 **사용자에게 투명하며, API 변경이 필요 없음**

## 언제 이득이 큰가?
* **작은 작업셋**을 가진 **짧은 서버/드라이버**들이 **IPC를 자주 하는** 워크로드에서 효과가 극대화됨
* **Large ↔ Large 전환**은 본질적으로 작업셋 재구축 비용이 커서, 이 방법으로도 완전히 상쇄되지는 않음 (그 구간은 기존 비용을 그대로 감수).

## 다른 CPU와의 대비(왜 접근이 다른가?)
* **ASID가 있는 CPU(MIPS 등)** 는 원래 전환 시 TLB 플러시가 필요 없으므로 이런 트릭이 크게 의미 없음
* **PowerPC**는 세그먼트 레지스터로 상위 주소 공간 교체를 직접 지원해 전환이 본질적으로 가벼움
* **486/Pentium**처럼 ASID가 없는 경우엔, **세그먼트 디스크립터 갱신**으로 **ASID**와 유사한 효과를 소프트웨어적으로 흉내 내는 것이 포인트

# Review Questions

### Sketch how you will implement a device driver using the primitives provided by Liedtke's microkernel.
#### Assumptions
* **A0 주소공간**: 물리 메모리와 장치 MMIO(메모리-맵 입출력) 영역을 있는 그대로 볼 수 있는 “물리 뷰” 주소공간.
* **커널이 주는 primitive** : 주소공간(태스크), 스레드, **동기 IPC**, 주소공간 연산 **map/grant/flush**
  * **map**: 내 것도 남겨둔 채 **공유** 매핑 만들기
  * **grant**: **소유권 통째로 양도**(보낸 쪽 매핑은 사라짐)
  * **flush**: **내 주소공간에서** 매핑 지우기(거기서 파생된 것까지 연쇄 무효화)
  
* **인터럽트=IPC**: 특정 IRQ가 오면 커널이 해당 “인터럽트 스레드”로 **짧은 메시지를 보냄** → 스레드가 깨어나 처리.

#### Steps
1. **드라이버 태스크/스레드 만들기**
   * 태스크 `kbdd`를 만들고,
   * **Top-half 스레드**(IRQ를 직접 받음) + **Bottom-half 스레드**(해석·발행)를 분리
     → 짧고 반드시 바로 해야 하는 일(레지스터 읽기)은 Top-half, 비교적 긴 일(스캔코드 해석, 구독자 통지)은 Bottom-half로 넘겨 **지연 격리**.

2. **장치 레지스터 매핑하기**
   * A0에서 키보드 **status/data 레지스터**가 들어있는 MMIO 페이지를 `kbdd`에 **grant**(독점이 필요할 때) 또는 **map**(공유가 필요할 때).
   * 규율: **한 주체가 책임지고 만지는 게 안전** (Integrity를 위해 독점 선호)

3. **IRQ를 드라이버에 묶기**
   * 커널에 `IRQ_KBD → kbdd.top`로 라우팅 설정. 인터럽트가 뜨면 **짧은 IPC**가 Top-half 스레드로 도착해서 즉시 깨어남

4. **Top-half(인터럽트 핸들러) 작업**
   * **status** 점검 → **data** 레지스터에서 스캔코드 읽기 → **lock-free 링버퍼**에 넣기 → 필요 시 장치 쪽 정리(EOI 등).
   * 링버퍼가 있는 페이지 `kbd_buf`는 **클라이언트(콘솔/윈도우 시스템 등)에 읽기 전용 map**으로 공유하거나, 소량 데이터면 IPC 페이로드로 바로 보냄. (교차 주소공간 복사가 필요하면, 커널의 임시 매핑 경로를 써서 **추가 맵 없이 복사** 가능.)

5. **Bottom-half(발행/서비스 API)**
   * 스캔코드 → 키 업/다운·조합키 상태로 해석, 자동반복 처리.
   * 클라이언트 요청은 **동기 IPC**로 응답: `READ(n)`, `SUBSCRIBE(필터)`, `GET_STATE()` 등.
   * 성능 팁: IPC는 스레드 전환=주소공간 전환이므로 **메시지 크기를 작게**(레지스터·작은 버퍼) 유지.

6. **보호와 회수(Integrity/Revocation)**
   * 클라이언트가 죽거나 공유를 끝내고 싶으면, 드라이버가 해당 페이지를 **flush**해서 상대쪽 매핑을 **무효화**.
   * 소유권 규율은 **grant/map/flush** 조합으로 깨끗하게 유지.

> **디스크로 확장**: 동일한 틀에 “요청 큐 + DMA 준비(PRD/SG 테이블) + 완료 인터럽트 처리 + 오류/타임아웃 재시도 + 필요 시 바운스 버퍼(grant로 확보)”만 얹으면 됨

### What is the difference between a "thread" as defined in Liedtke's paper and a Strand in SPIN?
* **L3/L4의 스레드**: 커널이 스케줄하는 **고정 단위**(특정 주소공간에 묶여 있음). IPC는 기본적으로 **동기**라서, 스레드 전환은 자주 **주소공간 전환**을 동반. 커널의 TCB가 전환에 필요한 커널 상태(페이지 테이블 루트 등)를 잡고 있음.
* **SPIN의 Strand**: 확장(라이브러리 OS)에게 내주는 **정책-주도형 스케줄 추상**. 쉽게 말해 “가상 CPU 조각”으로, 확장이 **자기 런큐/우선순위/규칙**을 얹어 **앱 맞춤 스케줄링**을 구현. 다만 **전역 스케줄러**는 CPU 배분의 최종 권한을 갖고 안전 보장

**핵심 차이**
* L3/L4 스레드 = **커널의 정해진 단위**.
* SPIN Strand = **확장이 정책을 얹을 수 있는 단위**(인-커널 안전 호출로 성능 유지).

### 전환 오버헤드 줄이기 (아키텍처에 맞춘 두 전략)
원문: Liedtke argues that a microkernel should fully exploit whatever the architecture gives to get a performance-conscious implementation of the microkernel. With this argument as the backdrop, explain how context switching overhead of a microkernel may be mitigated in modern architectures. Specifically, discuss the difference in approaches to solving this problem for the PowerPC and Intel Pentium architectures. Clearly explain the architectural difference between the two that warrant the difference in the microkernel implementation approaches.

공통 배경: μ-커널의 hot path는 **IPC → 스레드 전환 → 주소공간 전환**이고, 여기서 TLB 플러시/재적재가 비용을 키움. 그래서 **CPU가 주는 기능을 최대한 활용**해 전환을 가볍게 해야 함.

* **PowerPC(예: 601)**
  * **세그먼트 레지스터**가 상위 주소공간 문맥 교체를 **하드웨어 수준**에서 바로 도와줌.
  * 결과: 페이지 테이블을 갈아끼우지 않고 **가벼운 전환** 가능.

* **Intel 486/Pentium**
  * 기본: 페이지 테이블 루트를 바꾸면 보통 **TLB가 비워져서** 다시 채워야 하므로 비용이 큼.
  * **Pentium 최적화**: x86 **세그먼트 디스크립터(base/limit)** 만 바꿔서 **여러 “작은 사용자 공간”을 하나의 선형 공간 안에 공존**시키고, 전환 때 **CR3는 건드리지 않도록** 설계.
    * **Large↔Large** 전환은 기존 경로(비용 큼)
    * **Large↔Small / Small↔Small** 전환은 **세그먼트만 갱신**(비용 작음)
    * 사용자에게는 **완전 투명**, **API 변경 없음**

**왜 다른가?**
* PowerPC는 하드웨어가 “문맥 바꾸기”를 **직접** 지원.
* Pentium은 ASID가 없어서, **세그먼트 트릭**으로 사실상 ASID 같은 효과를 **소프트웨어적으로** 흉내 내는 접근을 택함.

### Explain the notions of "independence" and "integrity" in the L3 microkernel.
* **Independence**: 각 서브시스템은 **자기 주소공간/스레드**만 다루고, 상호작용은 **명시적 IPC**와 **명시적 map/grant**로만 함. **암묵 공유가 없으니** 구조적/장애 격리가 자연스럽게 됨.
* **Integrity**: **소유자만** 해당 자원(페이지 등)을 **map/grant/flush**할 수 있음. 또한 소유자는 자신에게서 **파생된 매핑**을 **flush**로 연쇄 무효화할 수 있어, **무단 수정 경로가 구조적으로 차단**.

### “grant(소유권 양도)”가 무결성을 해치나?
원문: All the subsystems in L3 live in user space. Every such subsystem has its own address space. The address space mechanism "grant" allows an address space to give a physical memory page frame to a peer subsystem. Can this compromise the "integrity" of a subsystem? Explain why or why not.

**해치지 않음**
* **grant는 자발적 소유권 이전**이라, 보낸 쪽 **매핑이 사라짐**. 즉, 그 페이지를 통해 보낸 쪽 상태가 더 이상 영향을 받지 않음(보낸 쪽 무결성 OK).
* 받는 쪽은 그 데이터를 **자신의 정책**에 따라 검증·사용하면 됨(데이터 출처 신뢰는 각자 정책 문제).
* 나중에 노출을 거둬들이고 싶다면, 소유권 흐름 위쪽에서 **flush**로 파생 매핑을 무효화하면 됨.

### "Trust in the L3 microkernel is transitive." Explain what this sentence means.

* 모두가 **커널의 참조 모니터**(규칙 집행자)를 신뢰한다는 것이 1차 전제
* 여기에 A가 B에게 **map/grant/IPC**로 **무언가를 공유**하면, 그 **공유 범위 안에서는** A의 올바름이 **B의 행위**에도 달리게 됨. 즉, **A → (커널, B)** 로 **신뢰 전이**.
* 중요한 점은 이 전이가 **명시적**이라서 **범위가 작고 추적 가능**하다는 것임. 그래서 μ-커널은 `최소 메커니즘 + 명시적 공유`를 고집.

### Microkernel based OS will always be less efficient compared to Monolithic kernel. True or False?  Explain your answer in detail.

**거짓**

* 성능은 구조보다 **구현과 하드웨어 활용**(TLB, 세그먼트, 트랩 경로)에 더 좌우됨.
* μ-커널도 **경계 횡단과 주소공간 전환을 얇게** 만들면 충분히 빠름(인터럽트를 IPC로 처리할 만큼).
* 모놀리식은 **커널 내부 공위치(co-location)** 덕을 볼 수 있지만, μ-커널도 **CPU 특성에 맞춘 경로 설계**로 충분히 대등하거나 더 빠를 수 있음.
