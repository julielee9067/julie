## 개요
SPIN: 애플리케이션이 커널 내부에 들어와(co-location) 필요한 정책과 구현을 직접 교체/확장할 수 있게 설계한 OS

- 안전성: **Modula-3**(타입 안전 언어) 기반의 **language safety(타입 안전성)**, **protection domain(보호 도메인: 코드가 볼 수 있는 이름 공간)**, **event/handler binding(이벤트-핸들러 연결)**, **capability(권한 토큰: 위조 불가 타입 포인터)** 로 확보
- 성능: **커널 주소 공간에 동적 링크**해 **함수 호출 수준의 비용**으로 내려감

## 배경
### 문제
* 범용 OS는 모든 앱에게 **하나의 정책**만 제공
* **특수 앱**(예: DB, 실시간 미디어)은 **다른 정책**이 더 적합. 기존 구조에서는

  * 여러 번의 **system call/IPC**(커널 호출/프로세스 간 통신) 왕복이 필요하거나,
  * **안전하지 않은 C 커널 모듈**로 커널을 직접 수정해야 했음

### 목표
**범용성**을 유지하면서 **확장 가능**하고 **안전**하며 **빠른** OS

### 접근법
* **확장성:** 필요한 지점만 **event/handler**로 갈아끼우기
* **안전성:** **Modula-3 타입 안전성 + protection domain + capability**로 확장 권한을 엄밀히 제한
* **성능:** 확장을 **커널 주소 공간**에 **동적 링크**하여 **함수 호출 비용**으로 실행

### 개발자가 실제로 하는 일
1. 바꾸고 싶은 **커널 이벤트** 선택
2. **같은 타입**의 **핸들러** 구현(필요하면 **guard**(실행 조건)로 범위 좁히기)
3. 커널은 **domain + capability**로 권한을 제한하고, **직접 호출** 수준으로 호출 경로 최적화

## Design Pillars
1. **Co-location**: 확장 코드를 **커널 주소 공간**에 **동적으로 링크**
2. **Modula-3**: 컴파일러가 **인터페이스 경계**를 강제 → 인터페이스가 허용하지 않는 메모리/자원 접근 **불가**
3. **Logical protection domains**: 코드와 그 코드가 볼 수 있는 **내보낸 인터페이스 집합**으로 **커널 레벨 네임스페이스**(namespace: 프로그램이 이름(symbol)으로 참조할 수 있는 범위) 정의
4. **Dynamic call binding via events**: 페이지 폴트, strand 스케줄링, 패킷 도착 같은 시스템 동작을 **이벤트**로 모델링. 확장은 **핸들러를 등록**하고, 조건이 단순하면 **직접 호출**로 최적화

> * **커널(kernel)**: OS의 핵심 부분. 자원 관리·스케줄링 담당
> * **네임스페이스(namespace)**: 프로그램이 볼 수 있는 **이름/심볼의 범위**
> * **Modula-3**: **타입 안전성**과 **모듈 인터페이스**를 엄격히 강제하는 언어
> * **Capability**: **권한을 담은 위조 불가 타입 포인터**
> * **Event/Handler**: **이벤트**는 호출 지점, **핸들러**는 그 지점에서 실행될 사용자 구현

## Protection model
**목표:** **주소 공간 전환 없이**도 **정밀 권한 부여**와 **격리** 달성. 권한은 **타입 안전 인터페이스**를 통해서만 부여.

* **Address space(주소 공간)**: 실행 중인 프로그램이 볼 수 있는 **가상 주소 전체 범위**. 각 주소는 **페이지 테이블**로 물리 메모리에 매핑됨.
* **Namespace(네임스페이스)**: 프로그램이 **이름(symbol)** 을 붙이고 참조하는 **범위/집합**.

> SPIN의 핵심: **주소 공간은 공유**하지만 **네임스페이스는 분리**하여 안전 보장
> (즉, 같은 메모리를 보더라도, **무엇을 부를 수 있는지**가 엄격히 다름.)

### 구성 요소
#### 1) Capability

* 커널 자원(객체, 인터페이스, 인터페이스 집합)을 가리키는 **위조 불가 타입 포인터**로 표현
* **특정 인터페이스에 한하여** 정확히 그 권한만 부여
* **포인터 전달 = 권한 위임**

#### 2) Externalized references(외부화 참조)

* **비-타입-안전**인 사용자 공간으로 커널 참조를 내보낼 때는 **프로세스별 테이블 인덱스**로 전달
* 커널이 이 인덱스를 **다시 타입 안전 포인터로 복구**
* 인덱스는 **권한 범위**를 넘지 않음

#### 3) Protection domain(보호 도메인)

* **코드 + 그 코드가 볼 수 있는 심볼 집합**을 묶는 **언어 레벨 네임스페이스**
* 도메인은 **export/import 인터페이스**를 **명시**

#### 4) 신뢰된 in-kernel linker(커널 내 링커)

* 도메인 간 **import ↔ export**를 **동적 바인딩**
* **TCB**(신뢰 기반 컴퓨팅 베이스)의 일부로, **타입 검증**과 **정책 검사** 수행

### 도메인 수명 주기
* **Create**: 검증된 객체 파일로 **새 도메인 생성**
* **Resolve**: 한 도메인의 **import**를 다른 도메인의 **export**에 **연결** (이때 **타입/정책 검사**)
* **Combine**: **둘 이상의 도메인 네임스페이스를 합집합**으로 묶어 한 번에 보이게 함

### 권한 부여/검사
* **최소 권한(least privilege)**: 기본적으로 코드는 **자신이 import한 인터페이스**로만 커널 상태에 영향
* **export/import control**: **export하는 쪽**이 **권한 검사 콜백**을 등록 → **누가 어떤 조건에서** 가져갈 수 있는지 **바인딩 시점**에 정책 적용

### 호출 비용
* **주소 공간이 동일**하므로 **인터페이스 경계**를 넘어도 **trap/context switch 없음**
* 결과적으로 **procedure call(일반 함수 호출) 수준의 비용**

## Extension model
**목표:** 커널 동작을 **이벤트**로 외부화하고, 확장이 **핸들러**를 끼워 정책을 **교체/보강**. 이때 **타입 안전성 + 도메인 + capability**로 안전 보장.

### 이벤트
* 정의: **인터페이스가 export하는 모든 프로시저**
* 어떤 이벤트를 볼 수 있는지는 **도메인 네임스페이스 + capability**로 결정

### Handler 등록 lifecycle
* 핸들러는 해당 이벤트와 **정확히 동일한 타입**을 가져야 함
* `InstallHandler(event, handler, guard?, constraints?)`로 설치 (제거는 같은 키로 언바인딩)
* 각 이벤트의 **기본 구현 모듈**이 **설치/제거 승인 또는 거부**

### Guard
* 역할: **이벤트 인자/상태**를 검사해 **일부 경우에만** 핸들러 실행
* 구성: 여러 조건의 **AND**로 구성(필요 시 **OR** 지원)

  * 예: `proto == UDP && dstPort == 9000`
* **IP 모듈**은 패킷 헤더의 **protocol type**을 guard로 생성해 **프로토콜별 핸들러 분리**
* **가드가 없고 핸들러가 한 개면 → 직접 호출**, 여러 개여도 **생성된 분기 코드**로 빠르게 평가

### Constraints
* **동기/비동기**

  * **동기**: 호출자 스택에서 즉시 실행(지연 짧음, **핫패스** 적합)
  * **비동기**: 별도 스레드에서 실행(긴 계산/IO **격리**)
* **Time bound(최대 실행 시간)**: 기본 모듈이 **최대 실행 시간**을 지정, **초과 시 중단**하거나 **비동기 전환**
* **Ordering(순서)**: 여러 핸들러가 있을 때 **실행 순서 지정**, 충돌 시 **기본 모듈 규칙**을 따름
* 커널은 **선점형**이므로 어떤 핸들러도 **CPU 독점 불가**

> * **핫패스(hot path)**: 자주, 빠르게 지나가는 핵심 실행 경로
> * **선점형(preemptive)**: 커널이 필요하면 실행 중인 작업을 **중간에 끊고** 다른 작업으로 전환할 수 있음

## 확장 가능한 핵심 서비스
### 1) Virtual Memory(가상 메모리) 분해 인터페이스

* **PhysAddr**: 물리 페이지 **관리**(할당/해제), **reclaim 이벤트**(회수 요청) 발행
* **VirtAddr**: 가상 주소 **범위 할당**, **주소/길이/ASID**(주소 공간 식별자) 포함 **capability 제공**
* **Transition**: **매핑 컨텍스트 생성** 및 **Add/Remove mapping**, 폴트 이벤트 **`BadAddress / PageNotPresent / ProtectionFault`** 발생

### 2) Thread and Strands

* **Strand**: 커널이 노출하는 **스케줄링 단위**(이름만 있고 필수 커널 상태 없음 → **경량 실행 문맥**)
* **Strand 인터페이스 이벤트**

  * **Block/Unblock**: 드라이버/인터럽트가 요청하는 **실행/비실행 가능 전환**
  * **Checkpoint/Resume**: 스케줄러와 스레드 패키지가 **실행 상태 저장/복원**
* **LibOS** 활용

  * **strands 위에 자체 thread package/scheduler 구현**(1:1 또는 M\:N)
  * **런 큐**, **TCB**(스레드 제어 블록), **strand별 메타데이터**, **동기화 구조** 유지
  * **resume**을 받으면 자체 런 큐를 돌려 **thread dispatch**, **checkpoint**를 받으면 상태 저장 후 **CPU 양보**

## How SPIN prevents resource hogging
### CPU 과점 방지
* 최종 권한자는 **global scheduler**(전역 스케줄러). 어떤 앱 스케줄러든 **checkpoint**로 즉시 중단 가능, **resume**을 받아야만 실행
* **time-bound handlers**: 기본 모듈이 **시간 제한** 또는 **비동기 처리**를 강제 → **장시간 작업**은 중단/off-loading
* **global CPU 정책**은 **신뢰된 코드**만 교체 가능(앱이 임의로 시스템 정책 변경 **불가**)
* **초기 매크로 정책 예시**: 특정 LibOS의 **scheduler strand**에 **우선순위/가중치** 부여 → **strand 수 제한** → **time slice** 할당 → 앱이 **global policy**를 임의로 교체하지 못함

### Physical memory 과점 방지
* **Capability 범위 할당**: LibOS는 **보유 capability** 안에서만 할당 가능
* **Reclaim 이벤트**: 물리 메모리 서비스가 언제든 **회수 요청**을 보낼 수 있음.

  * 핸들러가 **대체 페이지**를 제시할 수 있으나, **대상 페이지의 매핑은 무효화**
* **초기 매크로 제어**: 각 LibOS에 **페이지 예산**을 부여. **신뢰된 할당자**가 **성장 승인** 여부 결정 → **Reclaim**이 시스템 전체 **메모리 압력**을 집행 → 어느 하나의 LibOS도 다른 OS를 **RAM 기아 상태**로 몰아가지 못함

## 요약
* **네 기둥**: co-location, **강제 모듈화**(Modula-3 인터페이스), **protection domains**, **동적 이벤트 바인딩**
* **Capabilities** = **타입 포인터 권한 토큰**; 사용자 공간에는 **externalized reference 인덱스**로 전달
* **Domains API**: **Create/Resolve/Combine**; 바인딩 시 **권한 검사 콜백** 지원
* **Events/Handlers**: **guard**, **sync/async**, **time bound** 지원
* **VM**: **PhysAddr**, **VirtAddr**, **Transition**, **Fault 이벤트**, **Reclaim** 포함
* **Threads**: **Strand**, **Block/Unblock/Checkpoint/Resume**, **Global scheduler 우선 구조**
* **자원 제어**: CPU(Checkpoint, time bound), 메모리(capability, reclaim)로 과점 방지

## Review questions
### 1. SPIN의 extensibility에 필수적인 Modula-3의 기능은?
* **interface(encapsulation)**: 컴파일러가 **인터페이스/구현 경계**를 강제.
  → 확장은 **의도한 것만 노출**, 사용자는 **선언된 것만 사용** → **우발적 권한 누수 방지**
* **type safety(타입 안전성)**: 포인터는 **선언된 타입만** 가리킴(→ **capability**를 **타입 포인터**로 구현 가능)
* **자동 메모리 관리(GC)**: **use-after-free / type confusion** 방지

### 2. Strand의 정의와 LibOS에서의 활용법은?
* **Strand**: 커널이 아는 **최소한의 이름만 있는** 스케줄링 컨텍스트(필수 커널 상태 없음)
* **흐름 규정 이벤트**

  * **Block/Unblock**: 실행/비실행 가능 상태 전환
  * **Checkpoint/Resume**: 스케줄러↔스레드 패키지 간 **상태 저장/복원**
* **LibOS 활용**

  * Strands 위에 **자체 thread package** 구현
  * **resume**을 받으면 **런 큐**를 돌려 thread **디스패치**
  * **checkpoint**를 받으면 **상태 저장** 후 **CPU 양보**

### 3. SPIN이 CPU 과점을 방지하는 방법은?
* **Trusted global scheduler**가 **프로세서 배분**의 최종 권한
* **time-bound handler**: 기본 모듈이 **시간 제한/비동기**를 요구 → **장시간 핸들러**는 **중단**되거나 **off-loading**
* **초기 매크로 정책 예시**: 특정 LibOS의 **scheduler strand**에 **우선순위/가중치** 부여 → **strand 수 제한** → **time slice** 할당 → 앱이 **global policy**를 임의로 교체하지 못함

### 4. SPIN이 물리 메모리 과점을 방지하는 방법은?
* **Capability 기반 할당**으로 LibOS가 **만질 수 있는 범위**를 제한
* 물리 메모리 서비스는 언제든 **`Reclaim`** 을 올려 **페이지 회수**를 요구.

  * 핸들러는 **대체 페이지**를 제시할 수 있으나, **회수 대상 매핑은 무효화**
* **초기 매크로 제어**: 각 LibOS에 **페이지 예산**을 주고, **신뢰된 할당자**가 **성장 승인** 여부 결정 → **Reclaim**이 시스템 전체 **메모리 압력**을 집행 → 어느 하나의 LibOS도 다른 OS를 **RAM 기아**로 몰아가지 못함
