## 개요

> **Exokernel**: 커널은 보안만 담당(`"누가 어떤 자원을 써도 되는가?”`), **정책/기능은 앱 옆의 라이브러리 OS(LibOS)** 로 내려보내 각 앱이 자기 상황에 맞게 OS를 바꿔 쓰는 구조
* **빠른 이유**

  * 권한 확인을 **처음 한 번(바인딩 때)** 비싸게 하고, 그다음부터는 **짧은 표식(태그/엔트리)만 확인**해서 끝내기 때문(**secure bindings**)
  * 자원을 회수할 땐 먼저 알리고(**visible revocation**), 말을 안 들으면 **끊고 기록 후 복구를 촉구(abort)** 해서 **시스템 통제권**을 유지
* **커널 / LibOS**

  * 커널: **Aegis**
  * LibOS: **ExOS**

### 용어

| 용어             | 설명                                                              |
| -------------- | --------------------------------------------------------------- |
| **LibOS**      | 앱 전용 미니 OS. 파일/네트워크/스케줄링 등을 앱 내부 라이브러리로 구현해 링크해서 씀 |
| **Capability** | "이 자원을 이런 권한으로 써도 됨"을 증명하는 토큰                                   |
| **TLB/STLB**   | 주소 변환 캐시 (작은 하드웨어 캐시(TLB)) 앞단에 **큰 소프트웨어 캐시(STLB)** 를 두어 미스 비용 절감.                            |
| **PCT**        | Protected/cheap 교차 호출. 상대에게 남은 시간 조각을 기부하며 레지스터를 그대로 전달해 복사/문맥교환 비용 최소화.                                      |
| **DPF**        | 다운로드/컴파일 된 패킷 필터 (패킷 분류가 매우 빠름)                                 |
| **Scratch register**        | 함수 호출 간 보존되지 않아도 되는 임시 레지스터                                 |
| **Upcall**        | 커널 → 사용자 공간으로의 역방향 호출. 커널이 이벤트/예외/인터럽트 처리를 위해 **애플리케이션이 등록해 둔 함수(핸들러)** 를 직접 호출해 제어를 넘김                                 |

## 배경

* **커널 최소화**: 커널은 **primitive 자원(CPU, 물리 메모리, TLB, 예외/인터럽트, NIC)** 을 안전하게 여러 앱에 나눠주기만 함.
* **externalized policies**
  * VM/IPC/파일시스템/스케줄러 같은 **정책과 고급 기능은 LibOS**가 구현.
  * 앱이 필요한 것만 골라 쓰고, 내부 로직도 마음대로 바꿀 수 있음.
* **3요소**

  1. **Secure bindings**
    * 처음 연결할 때 신원확인·규칙설치(예: TLB 엔트리, 패킷 필터) → 이후 사용은 스티커 확인하듯 값만 체크.
    * 효과: 핫패스에서 검사 비용이 거의 0에 수렴.
    
  2. **Visible revocation**
    * 커널이 `“메모리 좀 돌려줘”`라고 정식으로 요청 → LibOS가 무엇을 반납할지 고르고 **자기 표(페이지 테이블 등)** 를 스스로 정리.
    * 효과: 커널-앱 상태 불일치가 줄어듦.
    
  3. **Abort**
    * 협조 안 하면 커널이 바인딩을 강제로 절단하고 `“무엇을 뺏었는지”` 기록을 남긴 뒤 예외를 올려 LibOS가 사후 복구하게 함.
    * 효과: 앱을 죽이지 않고 시스템을 안정하게 유지.
    
* **실험체**: **Aegis (커널) + ExOS (LibOS)** 로 실제 DECstation에서 **수치 비교**

## 설계 원칙

### 1) 보호 vs 관리의 분리
**커널=경비·출입 통제, LibOS=실사용 규칙/구현**

결과: 커널 인터페이스가 작고 안정적 → 빠르고 유연.

장점 예: 데이터베이스는 로그·버퍼 정책을, 게임은 스케줄링/메모리 핫패스를 각자 유리하게 교체 가능.

### 2) Secure bindings

**바인딩 시**: 권한증명(capability) 확인 + 짧은 코드/표식 설치(TLB 엔트리, DPF 등)

**사용 시**: 설치된 표식만 조회 → 시스템콜/트랩 없이 바로 통과 가능

**무효화 시**: 회수나 보안사유로 표식을 제거하면 이후 접근은 거부

### 3) Visible revocation

보이게 만들면 **LibOS가 자기 표를 즉시 갱신**하므로 `“커널은 회수했는데 앱은 모르는”` 불일치가 줄어 오류가 적음.

단, ASID처럼 상태가 없는 자원은 너무 자주 바뀌니 조용히(invisible) 바꾸는 편이 효율적.

### 4) Abort

LibOS가 응답이 느리거나 고의로 버틴다면:

  1. 커널이 바인딩을 끊고(자원 회수),

  2. Repossession vector(무엇을 뺏었는지 목록)에 기록,

  3. 예외를 올려 LibOS에게 `“이런 게 사라졌으니 표/상태를 고쳐라”`라고 통지.

이 절차로 시스템 전체는 멈추지 않음.

### 5) 공유 서버 최소화
공용 파일서버처럼 정책이 박히는 요소는 확장성의 적

가능하면 앱별 라이브러리로 분리해 정책을 다양화

### 6) 커널이 내주는 원시 기능 (Primitives)
Processor, Physical memory, TLB, Exceptions, Interrupts, DPF 기반 NIC

### 7) PCT (Protected Control Transfer)
* sync: 현재+다음 시간 조각까지 기부, 필요하면 반환.
* async: 남은 시간만 즉시 기부.
* 공통 보장: 원자적 도착, 앱이 보는 레지스터 불변 → 레지스터 자체가 메시지가 되어 복사/컨텍스트 스위치 비용 절감.
* 비유: 문서 보내기(IPC) 대신 **전화 통화(PCT)** 로 바로 말하는 느낌.

## Aegis 구현

* **예외 디스패치(업콜) 빠름**
  * 몇 개 스크래치 레지스터만 물리영역에 저장 → 유저 모드 핸들러로 점프.
  * 커널이 큰 프레임을 저장/복원하지 않아서 μs 단위로 빠름.
  
* **TLB 관리 + STLB**
  * TLB 미스 시 세그먼트/보장 여부를 먼저 본 뒤,
    * 보장 영역이면 커널이 즉시 TLB 설치(업콜 생략),
    * 아니면 LibOS 핸들러 호출
  * **STLB(4096 엔트리)** 가 용량 미스를 흡수 → 업콜 자체를 피하는 경우가 많아짐.* **PCT**
  
* **PCT**
  * Sync/Async 모두 지원, 레지스터 보존 + 시간 기부로 짧고 예측 가능한 경로.
  
* **DPF networking**
  * VCODE로 필터를 컴파일해 NIC 경로에 설치

## ExOS

* **제공 기능**
  * **Process, User-level exception, VM, IPC, Networking(ARP/RARP, IP, UDP, NFS)**
  
* **ExOS의 VM**
  * 약 1000줄로 구현했지만, 페이지 공유/별칭, 페이지별 캐시 정책, 특정 페이지 강제 할당, DMA까지 지원
  * 프로토타입 한계: 스와핑 없음, 선형 페이지 테이블(단순하지만 큰 작업셋에선 비효율 가능)
  * 커널이 정책을 강요하지 않으니, LibOS가 가벼운 핵심만 골라 성능 최적화에 집중할 수 있음

> 정책을 사용자 공간으로 끌어올려 커널 경로를 짧게 하고, 복사/컨텍스트 스위치를 줄여서 전체가 빨라진다.

## Review Questions

### 1. A library OS implements paged VM on Exokernel; an app hits a page fault. Walk the steps until resumption. (State assumptions and full path)

* **가정**

  * LibOS는 자체 페이지 테이블과 pager/backstore를 유지
  * fault 처리를 위한 코드와 메타데이터는 보장/pinned 영역에 존재 -> fault 처리 자체가 추가 fault를 유발하지 않도록
  * Aegis는 물리 페이지와 TLB 설치 작업에 대한 capability를 노출하고, 대용량 STLB로 매핑을 캐시함
* **단계**
```
TLB miss / page fault
   ├─ STLB hit? ──► 커널이 즉시 TLB 재설치 ──► 재개
   ├─ 보장 영역? ─► 커널이 즉시 TLB 설치 ───► 재개
   └─ 그 외 ─────► LibOS 핸들러 실행
                     ├─ 유효+상주 → TLB 설치 요청 → 재개
                     ├─ 유효+불재 → 프레임 할당/교체(필요시 회수 대응) → 재시도
                     └─ 무효     → 세그폴트 전달
```

  1. 폴트/미스 발생 및 신속한 예외 디스패치
     애플리케이션이 매핑되지 않은 가상주소에 접근하여 TLB 미스/페이지 폴트가 발생 -> Aegis는 소수의 스크래치 레지스터만 고정된 물리 영역에 저장하고, 폴트 원인/주소를 적재한 뒤 사용자 모드의 등록된 핸들러로 제어 이양
     
  2. 보장 영역 판정 및 커널 직접 설치
     문제의 가상주소가 보장 영역에 속하는지 검사. 해당하는 경우, Aegis가 업콜 없이 TLB 엔트리를 직접 설치하고 실행을 즉시 재개

  3. LibOS 핸들러의 페이지 테이블 검토
     LibOS 핸들러는 자체 페이지 테이블을 조회

       * 무효/권한 없음: 애플리케이션에 세그멘테이션 폴트 보고
       * 유효·상주(resident): 대상 물리 페이지에 대한 TLB 엔트리를 구성하고, 접근 권한을 증명하는 capability와 함께 TLB 설치를 Aegis에 요청

  4. 커널 검증 및 TLB 설치 후 복귀
     Aegis는 제출된 capability가 요청된 접근 권한과 일치하는지 검증 -> 검증 성공 시 TLB 엔트리를 로드하고, 사용자 모드로 복귀. 이후 폴트를 유발한 명령을 재시도
     
  5. 비상주 페이지 처리(가져오기 및 교체)
     * 페이지가 상주하지 않는 경우, 핸들러는 프레임 할당 또는 정책(예: LRU)에 따른 교체를 수행
     * 자원 압박 시, 커널은 visible revocation으로 페이지 회수 요청을 발행할 수 있음. LibOS는 반납할 페이지를 선택하고, 더티 페이지라면 백스토어 기록 후 자체 페이지 테이블을 갱신
     * LibOS의 지연·비협조 시, 커널은 abort-repossess 절차를 통해 바인딩을 강제 해제하고, 회수 내역을 repossession vector에 기록한 뒤 예외를 발생시켜 메타데이터 복구 요구 → 애플리케이션을 종료하지 않고도 시스템 일관성을 유지.

  6. 재시도 / 재개
     페이지가 상주 상태가 되면, 3–4단계를 반복하여 TLB 설치를 완료함 -> 핸들러는 반환되고, 폴트를 야기한 명령이 정상적으로 재실행됨.

### 2. “The high-level goals of SPIN and Exokernel are the same.” Why is that true?

* 둘 다 확장성(앱별 정책), 안정성(강한 격리/보호), 성능(hot path의 함수 호출 수준 overhead)을 지향
* 접근법은 다름. Exokernel: low-level primitives를 노출 + 보안 다중화 위에 LibOS 정책을 얹음. SPIN: 안전한 커널 내 확장(language enforced interface, dynamic kernel link, event/handler)으로 달성

### 3. Map Exokernel mechanisms to corresponding SPIN mechanisms

#### 1) Secure bindings → (SPIN) Typed capabilities + 1회 해석 후 직접 호출
* 권한 검증을 **바인딩 시점**에 끝내 두고, **사용 시점**에는 짧은 표식 확인만으로 접근을 허용하는 방식.
* **Exokernel**: TLB 엔트리·패킷 필터 등 **바인딩 때 인가**를 붙여 두어 이후 접근은 **값(태그) 확인만**으로 처리.
* **SPIN**: **타입이 붙은 포인터(capability)** 와 **동적 링크**로 인터페이스 이름을 **한 번만 해석**하고, 그 이후에는 **도메인 간 호출이 함수 호출 비용**으로 실행됨.
* **차이점**: Exokernel은 **저수준 자원**에 대한 커널 검증을 캐시하는 성격이 강하고, SPIN은 **언어(모듈/타입) 수준의 경계 강제**로 **이름 해석·권한 범위**를 고정해 둔 뒤 **직접 호출**로 비용을 줄임.

#### 2) Visible revocation → (SPIN) Reclaim 이벤트로 협력적 회수
* 자원 회수가 필요할 때 **애플리케이션 측이 무엇을 반납할지 관여**하고, **자기 메타데이터를 동기화**하게 하는 절차.
* **Exokernel**: 커널이 회수를 요청하면 라이브러리 OS가 **반납 후보 선택** 및 **페이지 테이블 갱신**을 수행.
* **SPIN**: 물리 메모리 서비스가 **Reclaim 이벤트**를 발생시키면 확장/라이브러리 OS가 **대체 페이지 제안**이나 **매핑 정리**를 수행.
* **차이점**: 양쪽 모두 **협력적 회수**를 통해 **상태 불일치**를 줄이지만, SPIN은 이 과정이 **이벤트/핸들러 규약**으로 명문화되어 있고, **언어 안전성** 덕분에 **권한 범위 밖 접근**이 구조적으로 차단됨.

#### 3) Abort protocol → (SPIN) 강제 회수 + 시간 제한 + 선점 스케줄링

* 회수 요청에 **응답하지 않거나 지연**될 경우, 커널이 **일방적으로 바인딩을 끊고** 상위에 **복구 신호**를 전달하는 안전장치.
* **Exokernel**: **바인딩 강제 해제**, **repossession vector** 기록, **예외로 복구 유도**(앱 종료 없이 시스템 일관성 보전).
* **SPIN**: 신뢰된 코어 서비스가 **강제 회수/제한**을 수행하고, **시간 제한 핸들러**와 **글로벌 스케줄러 선점(Checkpoint/Resume)** 로 **오남용을 즉시 제어**.
* **차이점**: Exokernel은 **저수준 바인딩을 끊는** 프로토콜 중심, SPIN은 **핸들러 실행 시간·스케줄링 권한**으로 **행동 자체를 제한**하는 경향이 강함.

#### 4) Protected Control Transfer(PCT) → (SPIN) 도메인 간 보호된 인커널 호출

* **개념**: 보호 경계를 넘는 제어 이전에서 **원자적 도착**, **레지스터 보존**, **낮은 호출 비용**을 보장하는 메커니즘.
* **Exokernel**: **동기/비동기 PCT**로 **시간 조각 기부**와 **레지스터 기반 메시지**를 지원(μs급).
* **SPIN 대응**: **동적 링크된 도메인 간 호출**이 **함수 호출 비용**으로 수행되며, **언어·모듈 경계**가 보호 역할을 수행.
* **차이점**: Exokernel은 **커널↔유저 간 저비용 전환**을, SPIN은 **커널 내(공주소공간) 도메인 간 직접 호출**을 최적화한다는 점이 다름.

#### 5) Primitive hardware 노출 → (SPIN) 세분 서비스 인터페이스(조립식)

* 커널이 **저수준 자원**을 직접 노출할지, 혹은 **작게 쪼갠 서비스 인터페이스**를 제공해 **조합**하게 할지의 차이.
* **Exokernel**: **CPU, 물리 메모리, TLB, 예외/인터럽트, DPF 기반 NIC** 등 **원시 자원**을 **보안 다중화** 형태로 제공. 라이브러리 OS가 **모든 고급 정책**을 구성.
* **SPIN**: **Phys/Virt/Translation**(VM), **Strands**(스케줄링), 각종 **이벤트/핸들러** 등 **미세한 인터페이스**를 제공하여 **필요한 조합만 선택**해 인커널 확장을 구현.
* **차이점**: Exokernel은 **정책 전권을 사용자 공간(LibOS)** 에, SPIN은 **정책을 커널 내 안전 확장**으로 끌어와 **직접 호출 성능**과 **언어적 안전성**을 동시에 확보.

### 4. How Exokernel’s mechanisms meet the high-level goals

#### 확장성(Extensibility)

* 커널은 **저수준 원시(primitive)** 만 안전하게 다중화하고, **공유 서버를 지양**. 고수준 정책·기능은 **앱별 LibOS**에 위임
* **효과**: 애플리케이션은 **자기 목적에 맞는 VM/IPC/FS/스케줄러**를 자유롭게 설계·교체. 커널 인터페이스가 단순·안정적이므로 **실험·특수화**가 용이
* **예시**
  * 데이터베이스: **페이지 교체 정책**, **버퍼 고정(pinning)**, **로그 I/O 배치** 등을 LibOS 차원에서 최적화.
  * 통신 스택: **DPF(동적 패킷 필터)**를 내려 설치하여 **애플리케이션별 분류 규칙**을 적용(공유 서버의 고정 정책에 종속되지 않음).

#### 안전성(Safety)
* **Secure bindings + Capability**로 **권한 검증을 바인딩 시점**에 마치고, 사용 시에는 **값(태그) 확인만**으로 접근을 허용. **Visible revocation**으로 회수를 **명시적으로** 수행하고, 필요한 경우 **Abort**로 **강제 일관성** 회복.
* **효과**: 권한 없는 매핑·패킷·인터럽트는 **구조적으로 차단**. 회수 시 LibOS가 **자신의 메타데이터(예: 페이지 테이블)** 를 직접 정리하여 **상태 불일치**가 줄고, 비협조 상황에서도 **Abort**를 통해 **시스템 안정성**을 유지(앱 종료는 최후 수단).
* **예시**
  * 메모리 압박 시 커널이 **회수 요청**을 발행하면, LibOS가 **반납 대상**을 선택하고 더티 페이지는 **백스토어 기록** 후 **테이블 갱신**. 지연 시 **Abort-repossess**로 바인딩을 끊고 **복구 예외**를 통해 정합성 확보.

#### 성능(Performance)
* **빠른 예외 디스패치(업콜)**, **STLB 기반 TLB 용량 미스 흡수**, **PCT(보호된 제어 전달)**, **DPF(컴파일된 패킷 분류)**.
* **효과**: 권한 검증·경계 횡단·주소 변환·네트워크 분류의 비용을 **핫패스에서 최소화**. 결과적으로 **μs급 제어 이전**, **낮은 VM 오버헤드**, **고속 패킷 디멀티플렉싱**을 달성.
* **예시**
  * **STLB** 적중 시 업콜 없이 **즉시 TLB 재설치**, **PCT**로 **레지스터 보존·시간 기부**를 포함하는 **저오버헤드 IPC**, **DPF**로 **10–20×** 수준의 분류 가속.

### 5. How SPIN’s mechanisms meet the high-level goals

#### 확장성(Extensibility)
* **Event/Handler 모델**과 **커널 내 동적 링크**로 확장을 **커널 주소 공간에 co-locate** 시킴. **세분화된 서비스 인터페이스**(예: **Phys/Virt/Translation**(VM), **Strands**(스케줄링))를 제공해 **조립식 정책 구성**이 가능.
* **효과**: 확장은 **기본 구현을 대체·후킹**하거나 **세밀한 단위(페이지, 스레드 전환 등)** 에서 정책을 바꿀 수 있으며, **가드(guard)** 와 **실행 제약**(동기/비동기, 시간 상한, 순서)을 통해 **상황별 분기**가 가능. **타입 안전성** 덕분에 커널 내부 확장임에도 **안전하게** 운용됨.
* **예시**
  * 네트워크 경로에서 **패킷 도착 이벤트**에 핸들러를 등록하여 **프로토콜별 특수 처리**를 직접 구현.
  * VM에서 **Translation** 인터페이스의 **fault 이벤트**에 대응하여 **특정 페이지 캐시 정책**을 삽입.

#### 안전성(Safety)
* **Modula-3**의 **타입 안정성**, **인터페이스 강제**, **보호 도메인(네임스페이스)**, **Typed pointer capability**. **Export/Import 인가 콜백**으로 바인딩 시 **정책 검사**를 수행.
* **효과**: 확장 코드는 **허용된 인터페이스 범위 내에서만** 접근 가능하며, **위조·경계 침범**이 언어 수준에서 차단됨. 도메인 간 호출은 **정적·동적 링크 시점**의 약속에 기반하므로 **권한 범위가 명확**함. **시간 상한** 및 **선점형 스케줄러**로 **오남용 제어** 가능.
* **예시**
  * 확장이 커널 객체를 직접 참조하려면 **capability(타입드 포인터)** 가 필요하며, 링크 시 **인가 콜백**을 통과해야 함. 과도 실행 시 커널이 **Checkpoint/Resume**으로 **즉시 회수**.

#### 성능(Performance)
* **공주소공간 내 호출**(동일 커널 주소 공간), **동적 링크** 후 **직접 호출(프로시저 콜 비용)**, **이벤트 디스패처 최적화**(단일 핸들러·무가드 시 **직접 점프**).
* **효과**: 경계 횡단 비용이 **메시지 IPC나 트랩**에 비해 **극히 작아** 핫패스에서 **정책 세분화**가 가능. 다중 핸들러·가드가 있어도 **생성된 호출 경로**로 비용 최소화.
* **예시**
  * **Strands** 기반 스케줄링에서 **응답성 요구**에 따라 **앱 전용 스케줄러**를 얹더라도, 글로벌 스케줄러와의 상호작용이 **함수 호출 수준**으로 가볍게 유지.
